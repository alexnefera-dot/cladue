# Генератор v5: двенадцать страниц по корпусу доноров

Цепочка целиком, из корня репозитория:

```bash
# 1. профиль корпуса: цели, полосы, граф ссылок, полоса уникальности
php engine/profil-v5.php                                  # → data-v5/profil-v5.json

# 2. библиотека виджетов и пулы прозы по разделам
php engine/bloki-v5.php --отчёт                           # → data-v5/bloki.json, pools.json

# 3а. сборка комплекта из пулов
php engine/generator-v5.php --выход=samples/v5-final/<имя> --сид=<n>

# 3б. или задание на написание — для реалайзера либо руками
php engine/zadanie-v5.php --выход=tmp/gen-<имя> --сид=<n>

# 4. доводка счётных величин
php engine/dovodchik-v5.php samples/v5-final/<имя> [--сухой]

# 5. приёмка формы и приёмка смысла
php engine/priyomka-v5.php samples/v5-final/<имя>
php engine/smysl-v5.php    samples/v5-final/<имя> [--подробно]

# 6. отчёты: «рядом» с разбором и «два текста» просто для чтения
php engine/ryadom-v5.php samples/v5-final/<имя>
php engine/dva-v5.php samples/v5-final/<имя>

# 7. переписать прозу разделов (нужен ключ; без ключа — --сухой)
php engine/realize-v5.php --набор=samples/v5-final/<имя>
```

Первые два шага делаются один раз на корпус, дальше работает третий.

---

## Что делает генератор

1. **Скелет** выбирается из наблюдённых сборок типа, взвешенно по частоте.
   Скелеты без известных виджетов (витрина `promo` у двух доноров) не берутся.
2. **Виджеты** переносятся разметкой один в один. Это не лень: у доноров они
   тоже общие, потому их главные и пересекаются между собой на 15.8 %. Внутри
   виджета меняются пары «вопрос-ответ» — они набираются из общего пула
   вперемешку по донорам.
3. **Проза** собирается по разделам и **по предложениям**, а не абзацами.
   Разница измерима: перенос целыми абзацами давал с ближайшим донором 16–26 %
   шинглов, сборка из фраз — 13–22 %. Шингл в шесть слов рвётся на границе
   предложения, и доля каждого донора падает втрое.
4. **Баланс доноров** — по словам, не по кускам. У `mellstroy` страница вдвое
   длиннее соседних, и при счёте кусками его доля в нашем тексте выходила 16 %
   против 3–4 % у остальных.
5. **Перетасовка**: восемь попыток на страницу, из них берётся лучшая. Попытка
   оценивается двумя числами — сколько полей профиля сошлось и насколько
   страница легла на одного донора; ворота по профилю первые, потому что самый
   непохожий вариант обычно и самый кривой по объёму.
6. **Прорези** заполняются из банков корпуса: каталог, число провайдеров и
   вейджер держатся на весь набор, герой — на раздел, суммы и RTP катятся на
   узел. «Джекпот до 47к» шесть пунктов подряд не пишет ни один донор.
7. **Журнал выдачи** `data-v5/vydano.json` помнит, что и в какой набор ушло:
   следующий набор берёт сначала невыданное. Отвергнутые попытки журнал не
   тратят.

Паспорт набора пишется рядом с страницами — `nabor.json`: сид, фактура, герои,
скелеты, попытки, замер по каждой странице.

## Чего сборка не может

Уникальность **покупается написанием, а не пересборкой**, и это считается на
пальцах. Страница набирается из фраз одиннадцати доноров; при идеальном балансе
доля каждого — около 100/11 ≈ 9 % текста, и все шинглы этой доли принадлежат
ему. Сверху ложится общая для всех библиотека блоков — ещё 5–7 %. Итого пол
пересборки ≈ 14 %, при том что сам корпус держит 6–11 %.

Замер сходится с арифметикой. Комплект `samples/v5-final/nabor-7`, сид 459,
после доводчика:

| страница | полей держат | профиль | совпало с ближайшим донором | потолок корпуса |
|---|---|---|---|---|
| `main` | 45/45 | 100 % | 19.5 % | 18.7 |
| `obzor` | 45/47 | 96 % | 16.4 % | 9.2 |
| `promo` | 46/47 | 98 % | 15.3 % | 10.2 |
| `news` | 45/47 | 96 % | 27.1 % | 8.9 |
| `info` | 43/45 | 96 % | 16.7 % | 8.3 |
| `partnery` | 47/47 | 100 % | 15.1 % | 10.3 |
| `app` | 48/48 | 100 % | 16.5 % | 9.9 |
| `bonus` | 45/47 | 96 % | 16.5 % | 2.3 |
| `registracia` | 49/49 | 100 % | 16.7 % | 9.4 |
| `slots` | 42/44 | 95 % | 15 % | 10.9 |
| `vhod` | 47/50 | 94 % | 21.4 % | 11.4 |
| `zerkalo` | 46/46 | 100 % | 17.9 % | 10.6 |

По форме и счётным величинам сборка попадает — 94–100 % полей профиля, из них
44–50 держимых на тип. По уникальности — нет: в корпусную полосу не выходит ни
одна страница, все держатся на 15–27 % при корпусных 6–11 %. В полосу сборки
(корпусный потолок плюс 100/доноров) укладываются девять из двенадцати.

Поэтому приёмка знает два порога. Набору со `способ: сборка` в `nabor.json` она
даёт корпусный потолок плюс 100/доноров и печатает корпусный рядом как ориентир.
Это не смягчение требования, а признание того, что пересборка ниже своей доли не
опустится.

| страница | ближайший свой | ближайший донор |
|---|---|---|
| `main` | 19.1 % (nabor-3) | 17.3 % |

мало: там свежее кончается втрое раньше, чем в среднем по пулу. Практический
предел одного корпуса — **семь наборов сборкой**, дальше нужен реалайзер.

### Сколько доноров нужно, чтобы выйти в корпусную полосу

Проверено подвыборками корпуса: пулы собирались из 4, 6, 8 и 11 доноров, по
каждому набору мерилось максимальное совпадение со «своим» корпусом.

| доноров | медиана совпадения |
|---|---|
| 4 | 26.9 % |
| 6 | 22.8 % |
| 8 | 20.1 % |
| 11 | 17.8 % |

Подгонка по четырём точкам (невязки меньше 0.5): **медиана ≈ 56.8/N + 12.9**.
Отсюда N = 24 даёт 15.3 %, N = 50 — 14.1 %, а асимптота — **12.9 %**. Это не
доля отдельного донора, а общий слой корпуса, который сборка набирает
неизбежно: сколько доноров ни собери, ниже тринадцати процентов пересборка не
опустится, а корпусная полоса — 6–11 %.

**Вывод: собирать доноров ради уникальности бессмысленно.** Работает только
написание прозы.

### Строгий журнал

Флаг `--строгий` запрещает брать куски, уже ушедшие в другой набор (пока свежего
вдвое больше нужного). Замер на трёх наборах подряд:

| режим | между нашими, средняя | между нашими, макс | страниц ≥95 % полей |
|---|---|---|---|
| обычный | 9.7 % | 22.3 % | 32/36 |
| строгий | 7.0 % | 12.1 % | 33/36 |

Каннибализация падает вдвое, профиль не страдает. Плата — на малых пулах: у
`vhod`, `news`, `info`, `app` и `zerkalo` всего по шесть разделов, и к третьему
набору свежие фразы там кончаются; в замере одна страница `vhod` ушла на 36 %
к донору, потому что выбирать было уже не из чего. Поэтому флаг не умолчание:
включать его стоит на первых трёх-четырёх наборах, дальше он начинает вредить.

### Что пробовали и не взяли

Выбор с оглядкой на недостающие черты: если странице не хватает `anchors` или
`imperatives`, предпочитать куски пула, где эти обороты есть. Идея выглядит
здраво — правится не текст, а выбор, — но замер на трёх наборах дал ровно тот же
результат (32 страницы из 36), а на одной странице ухудшил совпадение. Код снят:
недостающие черты в пуле просто не лежат, брать их неоткуда.

## Доводчик

`dovodchik-v5.php` правит только то, что нельзя испортить, — граница та же, что у
семистраничного: **трогает ли правка форму слова**.

Можно: эмодзи-маркер в начале пункта, тег списка `ul`↔`ol`, пары «вопрос-ответ»
целиком из пула, и сведение разных дробных процентов к уже встречающимся на
странице («RTP 97,2 %» → «RTP 96,8 %» — меняются цифры, плотность цифр остаётся).

Нельзя, уходит брифом писателю: `imperatives`, `anchors`, `on_topic_pct`,
`numbers_per100`, `anchor_once_pct`, `strong`, объём и абзацы. Всё это уже
пробовалось пакетным проходом в v4 — счётчики сходились, а в тексте появлялись
«второй регистрация».

Прогон по семи наборам поднял долю страниц, проходящих профиль, с 8–11 из
двенадцати до 11–12.

## Отчёт «рядом»

`ryadom-v5.php` кладёт наш комплект рядом с ближайшим донором — тем, с кем
среднее совпадение шинглов наибольшее. На каждую страницу две таблицы:

* **текст рядом** — обе страницы режутся на блоки (виджет, H2, H3, абзац,
  список) и выравниваются по типам через LCS; у блока стоит объём в словах и
  доля его шинглов, найденная у донора, так что видно не «похоже», а насколько;
* **все параметры** — полсотни полей `PageMetrics`: наше, донорское, цель
  корпуса, полоса p10–p90, держит ли поле фабрика и вердикт по коридору. Поля,
  которые фабрика не держит, показаны серым: расхождение по ним ничего не значит.

Готовый отчёт по седьмому набору — `reports/v5/ryadom-nabor-7.html`.

## Приёмка смысла

`smysl-v5.php` кодирует то, что раньше находилось только глазами. Проверок
восемь: незакрытые прорези любой формы (включая донорские `{NAME}`), числа вне
корпусных норм, ставка не меньше результата, единая фактура набора на всех
двенадцати страницах, род имени против рода глагола, один герой из двух
городов, метка анкора на трёх адресах, два почти одинаковых пункта рядом.

**Нормы сняты с корпуса, а не выдуманы:** RTP 92–99 %, бонус «до N%» 15–1000,
вейджер до x90, адресов ровно шесть.

**Проверка откалибрована по донорам** — и это оказалось важнее самих проверок.
Первый прогон нашёл у доноров семнадцать «дефектов», из которых настоящими были
только их незакрытые `{NAME}`. Остальное было ошибками проверок:

| что ловилось | почему это не дефект |
|---|---|
| «Ивана был» | родительный падеж мужского имени, а не женское имя |
| «Михаил сначала» | наречие на «-ла» — не глагол женского рода |
| «вейджер x3» | у кэшбэка вейджер и правда от x3 до x5 |
| «RTP 300 %» | конец одного пункта списка склеился с началом другого |
| метка на два адреса | 3 % меток корпуса так и устроены, «слоты» ведут и на «/», и на «/slots» |
| ссылка страницы на себя | у доноров главная ведёт на «/» 138 раз — это приём |

После правок на всех двенадцати донорах не остаётся ничего, кроме их
собственных прорезей. На наших восьми наборах — чисто.

Заодно проверка нашла свой первый настоящий дефект: «бонус до 13 %» при
корпусной полосе бонуса 15–1000. Оказалось, в банк процентов сваливались и
доли («кэшбэк 10 %»), и бонусы, а подставлялись они в одно и то же место.
Банки разведены — `ПРОЦ` для бонуса, `ДОЛЯ` для всего остального.

## Что видно только чтением

Отчёт `dva-v5.php` кладёт наш текст и донорский двумя колонками подряд, без
разбора на блоки и без цифр. Он не измеряет ничего — и именно поэтому нашёл
четыре дефекта, которые приёмка пропускала, потому что все счётчики по ним
сходились:

* **`{RTP2}` уезжал в выдачу.** Регулярка имени прорези не допускала цифр, и
  подстановка молча проходила мимо. Тем же дефектом страдала проверка приёмки
  на незакрытые прорези — она их не видела по той же причине.
* **«RTP 96.286 %».** Правило процентов откусывало хвост дробного числа
  карточки слота: целое от карточки, дробь от банка бонусов.
* **«RTP достигает 92 %».** Между словом «RTP» и числом стоит глагол, и
  лобовое правило уводило отдачу в банк бонусов, откуда приезжало «RTP 445 %».
* **«зашёл с 12 606 ₽ … довёл сумму до 12 606 ₽».** Ставка и результат берут
  одну прорезь, а `$банки` не была передана в замыкание сборки — лесенка
  значений молча не работала. Теперь ставка берётся из слоя до десяти тысяч,
  результат крупнее, и одно значение внутри узла дважды не выдаётся.

Отдача слотов заодно перестала кататься: у всех двенадцати доноров
`Sweet Bonanza` идёт с 96.51 %, и ростер после заполнения возвращается на место.

Вывод общий: **счётчики ловят форму, но не смысл.** Чтение двух текстов рядом —
не украшение отчётности, а обязательный шаг приёмки.

## Реалайзер: единственный путь в корпусную полосу

`realize-v5.php` переписывает прозу разделов в уже собранном наборе. Каркас при
этом не трогается, и это принципиально: виджеты у всех двенадцати доноров общие,
их надо воспроизводить, а не прятать; H2 — закрытый список фабрики; граф ссылок
и фактура набора уже посчитаны сборкой. Модели остаётся то, что и создаёт
совпадение, — тело раздела.

```bash
php engine/realize-v5.php --набор=samples/v5-final/<имя> [--тип=news] [--сухой]
php engine/dovodchik-v5.php samples/v5-final/<имя>
php engine/priyomka-v5.php samples/v5-final/<имя>
```

**Один вызов — один раздел, 250–450 слов.** Это не экономия, а требование:
замеры v4 показали разброс главной 63–84 % при одном и том же промпте, когда
страницу просят целиком; на коротком выходе реалайзер держится ровно. Комплект
из двенадцати страниц — 59 разделов, около 17–18 тысяч слов.

Промпт раздела собирается из того, что уже известно сборке:

* заголовок H2 (его переписывать не нужно — он из закрытого списка);
* сколько абзацев зачина, пунктов в списке и слов всего;
* адреса ссылок и их количество — **метку модель пишет своими словами**, потому
  что у корпуса 42 % анкоров встречаются ровно один раз, и списком это не
  воспроизвести;
* фактура набора: каталог, провайдеры, вейджер, герой раздела, и значения,
  которые в разделе уже стоят и должны остаться;
* жанр словами: разговор на «ты», история живого человека рядом с честной
  оговоркой про риск, без пафоса и восклицательных знаков. Половина полей
  профиля (`honest`, `cta`, `ty`, `numbers_per100`) — прямое следствие этих
  правил;
* потолок совпадения для этого типа страницы.

Промпты пишутся в `tmp/realize-<набор>/` всегда, в том числе при `--сухой`, —
их можно прочитать и поправить до боевого прогона.

**Отказоустойчивость.** Ключ проверяется до первого вызова. Если раздел не
написался — сбой сети, отказ модели, пустой ответ, — на его месте остаётся
собранный текст, и файл собирается заново без потерь: проверено побайтовым
сравнением. Три отказа подряд без единого успеха останавливают прогон.

Ключ читается из `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` либо из gitignored
`engine/.anthropic-key` — тем же кодом, что и у семистраничного `realize.php`.

## Второй путь: задание и написание вручную

`zadanie-v5.php` готовит то же, что `zadanie-v4.php` в семистраничном поколении,
— бриф на каждую из двенадцати страниц:

* скелет: какие виджеты в голове и хвосте, сколько разделов в теле;
* разделы: H2 из закрытого списка фабрики, в наблюдённом порядке, с числом
  абзацев зачина, фраз в абзаце и пунктов в списке;
* цели замера: поля профиля с `держат=true` и их коридоры;
* фактура набора: каталог, провайдеры, вейджер, герои — держится на весь комплект;
* бюджет ссылок и потолок уникальности.

Виджеты при этом всё равно собираются генератором: их разметка у доноров общая,
писать там нечего. Пишется проза тела и пары «вопрос-ответ» — это те 75 % текста,
которые и решают вопрос уникальности.

## Два дефекта подстановки, найденные по разбору промахов

Оба нашлись одинаково: берётся поле, которое мажет почти на каждом сиде,
и выясняется, откуда на странице берётся его значение. В обоих случаях
причина оказалась не в прозе, а в том, что генератор подставлял в готовый
донорский блок содержимое не из того пула.

### obzor: цитаты в блоке отзывов

Скелет obzor вызывает `review-quotes-block` — четыре раскрывающихся отзыва
игроков, под каждым заголовком реплика в кавычках. Блок доходил до страницы,
но перебор виджета заполнял реплики записями из пула `раскрывашки`,
собранного с других виджетов: двадцать записей, ни одной кавычки, содержание
методическое. Под заголовком «Выплаты и верификация» вставал абзац о том,
как считается рейтинг, а четыре донорские реплики исчезали целиком.

obzor — единственный тип, где цель по `speech` ненулевая (5 при полосе 4–8);
у остальных одиннадцати она 0, то есть запрет. Страница входила в приёмку с
уже потраченным промахом: `speech` мазал во всех девяти наборах партии
244–253 подряд, 0–2 при цели 5.

Заодно регулярка заголовка искала `<span>`, а в разметке
`<span class="review-quote-summary">` — она не совпадала ни разу, и все
наборы несли четыре донорские метки дословно.

Решение: пул `хвосты.obzor.цитаты`, 48 реплик по двенадцать на четыре темы,
метки все разные, прорези `СУММА`, `МИН`, `ВЕЙДЖЕР`, `ПРОЦ`. `Раскрывашки`
остались запасным источником для типов без своего пула.

Замер, 12 сидов, обе ветки на одних сидах, журнал откатывается после каждой
сборки:

| | до | после |
|---|---|---|
| реплик в кавычках на obzor | 1.3 | 5.2 |
| `speech` в списке промахов | 12/12 | 0/12 |
| совпадения obzor | 13.8 % | 13.0 % |
| страниц прошло приёмку | 9.42 | 9.67 |

По совпадениям ниже или без изменений на 11 сидах из 12. Сам пул цитат
против доноров 0.9–1.1 %, против всего архива максимум 1.6 %.

### vhod: длина реплик в layout-block

Метрика `para_short` считает абзацы короче пятнадцати слов. У всех двенадцати
доноров на vhod ровно два таких абзаца, и это элемент шаблона, а не разброс.
Четыре реплики `layout-block` у доноров имеют длины 26, 23, 16 и 15 слов —
ни одной ниже порога, одинаково у всех двенадцати.

Наши реплики берутся из `хвосты.vhod.раскрывашки`, и одиннадцать записей из
двадцати четырёх были короче пятнадцати слов. При четырёх слотах на страницу
это добавляло к шаблонным двум ещё два-четыре коротких абзаца.

Решение: одиннадцать записей дописаны до 15–26 слов, разброс длин сохранён.

Замер, 20 сидов, те же сиды в обеих ветках:

| | до | после |
|---|---|---|
| коротких абзацев на vhod | 5.75 | 2.75 |
| `para_short` в промахах | 20/20 | 0/20 |
| vhod прошёл приёмку | 4/20 | 12/20 |
| средний процент полей vhod | 93.1 % | 95.1 % |
| страниц прошло приёмку | 9.70 | 10.10 |

Совпадения vhod не изменились: 9.26 % против 9.27 %, хуже стало на 4 сидах
из 20.

### Что осталось на vhod

После правки первое место занял `h3_question_pct` — 14 промахов из 20, у нас
76.2 при цели 40.9. Заголовки h3 в разделах вопросительные в 0.6 % случаев
(1 запись из 161), то есть все вопросительные h3 приходят из виджета FAQ, и
доля зависит от того, какой вариант выпал: часть вариантов размечает вопросы
через `<h3>`, часть через `<button><span>`.

Гипотеза о задвоении блока FAQ — класс `faq-list` записан в скелете рядом с
`faq-section`, а в разметке лежит внутри него — проверена на 54 наборах и не
подтвердилась: везде ровно один блок.

Отдельно стоит знать, что коридор приёмки по этому полю ±10.2 вокруг 40.85,
то есть 30.7–51.1, а сами доноры дают от 25.0 (vodka) до 55.6 (pinco). Двое
из двенадцати доноров не прошли бы собственную приёмку по этому полю, так что
часть промахов здесь — узкий коридор в профиле, а не кривизна сборки.
Расширять его задним числом нельзя без оглядки: цели принятых наборов
заморожены в паспорте.

Ещё одна мелочь того же рода: `faq` и `questions_total` — это одно и то же
число, `substr_count($text, '?')`, посчитанное дважды. Недобор вопросов стоит
странице сразу двух полей из пятидесяти.
