# Pipboy — обзор безопасности (перед упаковкой)

Дата: 2026-06-17. Модель угроз: полностью локальное персональное приложение,
два устройства одного владельца (Mac + iPhone), синхрон по домашней Wi-Fi.
Вся база — под SQLCipher, доступ к приложению — за Face/Touch ID.

Проверены: обход пути в `pipboy://`, SQL-инъекции, XSS во фронте,
крипто-канал и доверие при синхроне, согласованность временных меток (LWW/tombstones),
хранение ключей в Keychain.

---

## Подтверждено безопасным

- **Обход пути (path traversal) в схеме `pipboy://`** — `staticFile()` сводит путь
  через `standardizedFileURL` (резолвит `..` ДО проверки) и требует префикс веб-корня
  с `/`. Выход за корень даёт 404. Чисто.
- **SQL-инъекции** — все значения идут через `?`-параметры. Имена таблиц/колонок
  интерполируются только из жёстких списков-белосписков и схемы, не из пользовательских
  данных. Чисто.
- **Markdown-рендер заметок (`mdRender`)** — экранирование (`nesc`) выполняется ДО
  генерации HTML; `inline()` работает уже по экранированному тексту. `<script>`,
  `<img onerror>`, `javascript:`-ссылки не проходят. Чисто.
- **Крипто-канал** — X25519 ECDH + AES-GCM со случайным nonce на каждое сообщение,
  без повторного использования nonce. Атомарность слияния — единая транзакция с ROLLBACK.
  Авто-бэкап базы (10 копий) делается ДО разрушающего слияния.

## Исправлено в этом проходе

| # | Было | Стало |
|---|------|-------|
| Меткаs времени (latent data-loss) | `nodes.updated_at` / `pages.updated_at` имели DEFAULT в UTC (`datetime('now')`), что в обход localtime-триггера могло сделать новую строку «старее» tombstone → исчезновение после синхрона | DEFAULT приведён к `datetime('now','localtime')` — как и все остальные метки в коде (`Database.swift`) |
| DoS кадром (любой пир в сети) | длина кадра — `UInt32` без потолка → заявленные ~4 ГиБ копятся в память → OOM-краш | потолок кадра 256 МБ, иначе соединение рвётся (`NativeAPI.swift recv`) |
| Доверие колонкам пира | строка от пира с неизвестной колонкой роняла всю транзакцию слияния | неизвестные колонки отбрасываются (`knownKeys` по схеме), слияние устойчиво; заодно — forward-compat при добавлении полей |
| Подмена фронта непарным устройством (code exec) | любой успешный обмен принимал веб-фронт пира и записывал в `webDir` | фронт принимается ТОЛЬКО от уже доверенного пира (`applyWeb: trusted`) |
| XSS defense-in-depth | esc-хелперы не экранировали `'` | все 8 хелперов экранируют `'` → `&#39;` |
| Опасные схемы в заметках | `htmlToMd` тащил `<a href="javascript:…">` в markdown | `javascript:`/`data:`/`vbscript:` отбрасываются при вставке |

## Известные ограничения — на следующий этап (требуют UI/архитектурных изменений)

Сознательно отложено: модель угроз (домашняя сеть, свои устройства) делает риск
приемлемым для текущей упаковки, а исправления затрагивают протокол и UI — это
отдельная работа уже на фазе «вносим функционал».

1. **SAS-код показывается, но не подтверждается (CRITICAL по строгой модели).**
   `handshake` выводит 6-значный код и сразу шлёт снимок — обмен не ждёт, пока
   пользователь сверит коды. В окне ПЕРВОЙ ручной связки устройство на той же Wi-Fi
   может получить полный обмен, а MITM — релеить. Авто-режим уже защищён (только
   доверенный пир). **Фикс:** добавить действие `confirmSas` (кнопка «коды совпали»
   на обоих устройствах) и не отправлять снимок / не запоминать пир до подтверждения.
   Файлы: `NativeAPI.swift` (`handshake`, `finish`), `WebView.swift` (мост действий).

2. **Коллизия переиспользованных id между устройствами (data-corruption).**
   `INTEGER PRIMARY KEY` без `AUTOINCREMENT`: две оффлайн-вставки на разных
   устройствах получают одинаковый id → LWW считает их одной строкой → одна теряется.
   **Фикс:** UUID или device-префикс в ключах синхронизируемых строк.

3. **LWW по локальному времени без логических часов (data-loss при рассинхроне
   часов / разных таймзонах).** Сравнение строк localtime двух устройств не
   монотонно. **Фикс:** хранить метки в UTC, конвертировать только для показа;
   добавить тай-брейк `(updated_at, device_id)` или счётчик; использовать уже
   передаваемый `generated_at` для контроля перекоса часов.

4. **Замок секций — несолёный SHA-256, хеш возвращается веб-слою.** В нативе это
   мягкий UI-гейт поверх биометрии + SQLCipher (не криминал), но в браузерной/дев-версии
   хеш служит API-ключом. **Фикс (если усиливать):** per-install соль + scrypt
   (он уже есть в `Crypto.swift`), не возвращать хеш в ответе.

5. **`Database.sqlcipherActive` определён, но не проверяется.** Если продукт SQLCipher
   не привязан к таргету — приложение молча работает на ОТКРЫТОМ SQLite.
   **Проверка при упаковке:** убедиться, что в release-сборке обоих таргетов
   `sqlcipherActive == true` (см. чек-лист ниже).

6. Прочее (low): нет GC tombstones (растут без ограничения, но это защищает от
   воскрешения), tie-LWW расходится на равных метках, pre-merge бэкап best-effort.

## Чек-лист упаковки (безопасность)

- [ ] Продукт **SQLCipher** привязан к обоим таргетам (macOS + iOS); проверить, что
      `Database.sqlcipherActive == true` в release (иначе база НЕ шифруется).
- [ ] Info.plist: `NSLocalNetworkUsageDescription`, `NSBonjourServices=_pipboy._tcp`,
      `NSFaceIDUsageDescription` присутствуют.
- [ ] Keychain: основной ключ — за биометрией; recovery-копия `db-key-recovery` —
      `WhenUnlockedThisDeviceOnly`, не синхронизируется в iCloud.
- [ ] Синхрон: первая связка делается осознанно дома; до п.1 выше не пользоваться
      пэйрингом в недоверенной сети.
