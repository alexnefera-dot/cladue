# Непотопляемая архитектура редиректора

## Суть

Раньше: каждый клик `/go/*` = запрос к MySQL (чтение оффера + запись клика).
Под нагрузкой/DDoS база захлёбывалась → редиректы падали (522).

Теперь: **редирект вообще не трогает базу.**
- Офферы читаются из файла-кэша `offers.php` (мгновенно).
- Клик пишется одной строкой в файл `clicks.log` (атомарный append).
- Раз в 5 минут крон-скрипт `import.php` переливает лог в MySQL.

**Результат:** MySQL может лежать, тормозить, быть под DDoS — редиректам всё равно.
Они зависят только от файловой системы, которая тянет любой поток.

## Поток данных

```
Юзер → /go/dorgen_engine
         │
         ├─ go.php читает оффер из offers.php (файл, без БД)
         ├─ пишет клик строкой в clicks.log (append, без БД)
         └─ отдаёт 302 → партнёрка
                            
Крон (раз в 5 мин):
   import.php: clicks.log → MySQL (батч), потом чистит лог
                            
Панель stats.php: читает из MySQL (задержка до 5 мин)
```

## Файлы

| Файл | Что делает | Трогает MySQL? |
|------|-----------|----------------|
| `go.php` | редирект + запись клика в лог | **НЕТ** |
| `offers.php` | автогенерируемый кэш slug→URL | — (это данные) |
| `clicks.log` | накопитель кликов (TSV) | — (это данные) |
| `import.php` | крон: лог → MySQL | да (раз в 5 мин) |
| `stats.php` | панель | да (чтение) |
| `postback.php` | приём постбеков | да (запись конверсий) |
| `db.php` | общие функции + генерация offers.php | да |

## Установка

### 1. Залей файлы
`go.php`, `db.php`, `import.php`, `config.php` (+ `stats.php` если обновлял).

### 2. Настрой config.php
Проверь/добавь:
```php
'db_write'    => true,           // писать клики (в лог)
'fallback_offer' => '',          // пусто (аварийный режим выключен)
'click_log'   => __DIR__ . '/clicks.log',  // путь к логу (или оставь дефолт в tmp)
```
И убедись, что MySQL-креды заполнены (mysql_db, mysql_user, mysql_pass) — они
нужны для import.php и панели.

### 3. Построй кэш офферов первый раз
Открой в браузере (один раз):
```
https://sitegrator.com/import.php?key=ТВОЙ_POSTBACK_SECRET
```
Это создаст `offers.php` из текущих кампаний в базе. Проверь, что файл появился.

Или зайди в панель и пересохрани любую кампанию — кэш построится автоматически.

### 4. Настрой крон
ispmanager → CRON jobs → Create plan:
- Команда: `/opt/php82/bin/php /var/www/www-root/data/www/sitegrator.com/import.php`
- Расписание: раз в час → `0 * * * *`

⚠️ **ВАЖНО: только `/opt/php82/bin/php`, НЕ `/usr/bin/php`.**
Системный `/usr/bin/php` на этом сервере — PHP 7.2, он не понимает стрелочные
функции (`fn()`) в db.php и падает с `PHP Parse error: unexpected '=>'`.
Импорт при этом умирает молча (вывод уходит в `>/dev/null`), клики копятся
в clicks.log и не попадают в базу — в панели выглядит как «клики не пишутся».
Проверить версию: `/opt/php82/bin/php -v` → должно быть 8.2.x.

Сохрани. Теперь клики автоматически переливаются в базу раз в час.

### 5. Проверь
```
# редирект работает и пишет в лог:
curl -sI "https://sitegrator.com/go/dorgen_engine" | grep -i location

# лог наполняется (зайди в файловый менеджер, глянь clicks.log — растёт)
# через 5 минут (или запусти import.php вручную) клики появятся в панели
```

## Как работает защита от падений

- **Пик трафика ×100** → go.php только пишет строки в файл (дёшево). Держит.
- **DDoS на /go/** → то же самое, файл тянет тысячи строк/сек. Держит.
- **MySQL лёг** → клики копятся в clicks.log. Редиректы работают. Когда MySQL
  оживёт, import.php всё зальёт. Ничего не теряется.
- **Крон не отработал** → клики просто копятся в логе дольше, зальются следующим
  запуском. Не теряются.
- **import.php упал на середине** → использует .processing файл, докатит при
  следующем запуске.

⚠️ Оговорка про .processing: импорт коммитит пачками по 500 строк. Если процесс
**прервать вручную** (Ctrl-C) посреди заливки большого лога, уже закоммиченные
пачки останутся в базе, а `.processing` не удалится — следующий запуск зальёт
файл целиком заново и получатся дубли. Не прерывай импорт: на 100k кликов он
идёт ~1.5 минуты и после `offers.php обновлён` работает молча (это норма, не
зависание). Если дубли всё же появились — почистить так:

```sql
DELETE c1 FROM clicks c1 JOIN clicks c2
  ON c1.clickid = c2.clickid AND c1.id > c2.id
WHERE c1.clickid <> '' AND c1.clickid IS NOT NULL;
```
(clickid — 64-битный рандом, совпадение = повторный импорт, а не два разных клика)

## Аварийный режим (если совсем всё плохо)

Если даже запись в лог не нужна и надо просто слать всех на один оффер:
```php
'db_write'       => false,
'fallback_offer' => 'https://fnx-abs.net/di6viifma',
```
Тогда go.php даже лог не пишет — чистый редирект на один URL. Максимальная
разгрузка.

## Кэш панели (почему stats.php больше не тормозит)

Клики попадают в MySQL только при импорте (крон, раз в час) — значит между
импортами агрегаты панели не меняются, и пересчитывать их на каждую
перезагрузку бессмысленно.

Замер на боевой базе (889k кликов, период «Сегодня») до кэша — **6.4 с**:

| запрос | было | доля |
|--------|------|------|
| `daily_stats(30)` — график за месяц | 2918 мс | 45% |
| сводка по кампаниям (GROUP BY slug) | 1480 мс | 23% |
| `lastByCamp` — MAX(ts) по всей таблице | 972 мс | 15% |
| `geo_by_campaign` | 392 мс | 6% |
| `service_health` | 364 мс | 6% |
| `geo_stats` | 292 мс | 5% |

Теперь эти результаты складываются в `cache/*.cache` (`panel_cache()` в db.php).
Ключ кэша включает метку `meta.last_import`, которую пишет import.php — поэтому
после каждого импорта кэш инвалидируется сам, а между импортами панель отдаёт
готовое. Первый заход после импорта считает по-настоящему, дальше — из файла.

**Прогрев.** После импорта метка меняется, то есть весь кэш инвалидируется — и
первый заход в панель иначе ждал бы полного пересчёта (на боевой базе это
доходило до 12 с, вплоть до таймаута). Поэтому import.php после импорта сам
вызывает `panel_cache_warm()`: считает агрегаты по всем четырём периодам
(today/yesterday/7d/30d) плюс график, health и lastbycamp — 15 ключей. Панель
всегда открывается из готового кэша.

Прогрев идёт из крона (root), а панель работает под www-root — поэтому
`panel_cache()` при записи из root переставляет владельца файлов (и каталога
`cache/`) на владельца config.php, иначе панель не смогла бы обновить кэш.

- `panel_cache_flush()` вызывается при правке кампаний и очистке истории —
  иначе панель показывала бы устаревшие цифры.
- Кэш пишет только веб-процесс (www-root). Крон эти функции не вызывает, так
  что конфликта прав root/www-root нет.
- `cache/` закрыт в .htaccess и не версионируется.
- Не кэшируется то, что и так быстро: `recent_conversions` (~5 мс),
  `conversions_by_slug/totals` (~2-3 мс), `recent_gaps` (~14 мс).

## Привязка постбеков (почему были «не привязанные» реги)

Постбек от партнёрки приходит через считанные минуты после клика, а клик
доезжает до MySQL только с импортом (раз в час). `record_conversion()` в момент
постбека клика не видит и пишет `slug = NULL` — в панели это «не привязан».
Раньше привязка после импорта не пересчитывалась, и конверсия оставалась
непривязанной навсегда.

Теперь import.php после заливки кликов вызывает `relink_conversions(7)` —
она подставляет slug клика конверсиям с пустым slug. Разовая привязка всей
истории: `relink_conversions(0)`.

Остаются непривязанными только те конверсии, у которых клика в базе нет вовсе
(например, пришли в период, когда импорт не работал, или партнёрка потеряла
clickid на своём редиректе).

### Постбеки: рега и первый деп (FTD)

В кабинете партнёрки настраиваются ДВА постбека — на событие «Регистрация» и на
событие «Первый депозит»:

```
рега: https://sitegrator.com/postback.php?key=СЕКРЕТ&cnv_id=${clickid}&cnv_status=reg
деп:  https://sitegrator.com/postback.php?key=СЕКРЕТ&cnv_id=${clickid}&cnv_status=dep
```

Оба события пишутся в `conversions` отдельными строками с одним и тем же
clickid. Считаются они независимо по `status`, поэтому **деп ничего не отнимает
у регистраций** — у одного игрока штатно бывает и рега, и деп.

Какие значения `status` к чему относятся:
- реги: `reg`, `registration`, `lead`
- депы: `dep`, `deposit`, `sale`, `ftd`, `purchase`

Сумму депозита не передаём (`payout` остаётся 0) — нужен только факт FTD.
Если понадобится хранить сумму, партнёрка отдаёт её как `${amount}`, а
postback.php читает её из `payout`/`sum`/`amount`; валюта нигде не хранится,
поэтому суммы в разных валютах сложатся вперемешку.

В панели депы выведены везде, где были реги: колонки «Депы» и «🇷🇺 Депы» в
сводке по кампаниям, счётчики в шапке (с пометкой непривязанных), линии на
графике за месяц, колонка «Депы» в источниках, колонка «Событие» (рега/деп) в
«Последних постбеках» и поле `deps` в CSV-экспорте. Цвет депов — оранжевый
(реги фиолетовые, юзеры зелёные).

## Инцидент: сервер падал, error.log рос до 1.6 ГБ

Симптомы: сайт периодически ложился целиком (включая редиректы), в
`/var/www/httpd-logs/sitegrator.com.error.log` — гигабайты, в них
`AH01220: Timeout waiting for output from CGI script`.

**Причина оказалась не в коде проекта, а в конфиге PHP сайта.** В
`/var/www/php-bin-isp-php82/www-root/sitegrator.com/site.ini` было прописано
`extension=sqlite3.so`, но такого модуля в PHP 8.2 на сервере нет (есть только
`pdo_sqlite.so`). Каждый запуск PHP-CGI — то есть КАЖДЫЙ клик по рефке —
спотыкался об это и писал строку в error_log:

```
198 528 строк из 200 000 (99.3%) = PHP Warning: Unable to load dynamic library 'sqlite3.so'
всего в логе: 3 010 777 строк, из них таймаутов CGI: 317
```

При потоке редиректов это миллионы записей на диск в час. Постоянный I/O плюс
лишняя работа на старте PHP → под пиком Apache копил процессы → nginx получал
`upstream timed out` и `connect() failed` → сайт лежал.

Лечение (одна строка):
```bash
INI=/var/www/php-bin-isp-php82/www-root/sitegrator.com/site.ini
cp $INI $INI.bak
sed -i 's/^extension=sqlite3\.so/;extension=sqlite3.so/' $INI
truncate -s 0 /var/www/httpd-logs/sitegrator.com.error.log
```
`pdo_sqlite.so` НЕ трогаем — он рабочий, и именно он нужен sqlite-ветке db.php
(класс `SQLite3` в коде не используется, только PDO). Проект всё равно на MySQL.

Результат: error.log перестал расти вообще (0 байт за минуту под нагрузкой).

⚠ ispmanager может перегенерировать `site.ini` при изменении настроек PHP сайта
через панель. Если warning вернётся — убирать sqlite3 уже в настройках
расширений сайта в самом ispmanager.

Поставлена ротация, чтобы логи в принципе не разрастались:
`/etc/logrotate.d/sitegrator` — `size 200M`, `rotate 3`, `compress`, `copytruncate`.

### Как быстро найти, кто забивает лог

Не выгружать гигабайты, а схлопнуть строки по смыслу (режем pid, client и все
числа — тогда одинаковые ошибки сгруппируются):

```bash
LOG=/var/www/httpd-logs/sitegrator.com.error.log
tail -200000 $LOG \
  | sed -E 's/^\[[^]]*\] //; s/\[pid [0-9]+(:tid [0-9]+)?\] //; s/\[client [^]]*\] //; s/[0-9]+/N/g' \
  | cut -c1-110 | sort | uniq -c | sort -rn | head -12
```

Проверить, виноват ли крон (он в :00) — распределение таймаутов по минуте часа:
```bash
grep -F "AH01220" $LOG | awk '{print $4}' | cut -d: -f2 | sort | uniq -c | sort -rn | head
```

## Защита от перегрузки сервера

Крон делает тяжёлую работу (импорт, агрегаты, очистка), поэтому предусмотрено
четыре предохранителя:

**1. Блокировка запусков.** `import.php` берёт неблокирующий `flock` на
`cache/import.lock`. Если база разрастётся и заход не уложится в час, второй
экземпляр не полезет поверх первого (два процесса с тяжёлыми `COUNT DISTINCT`
положили бы MySQL, а с ним панель и приём постбеков) — он просто выйдет с
сообщением, и работу догонит следующий запуск. Блокировка снимается ОС даже
при `kill -9`.

**2. Бюджет прогрева кэша.** `panel_cache_warm(30)` прогревает ключи по
приоритету: сначала главная за «сегодня» и график (их открывают почти всегда),
потом вкладка настроек, и только затем длинные периоды (7d/30d). Если 30 секунд
вышли — остаток не считается, он досчитается лениво при первом открытии. Так
крон не растягивается на минуты и не держит MySQL дольше необходимого.

**3. Очистка старых кликов — только из крона и пачками.** Раньше
`maybe_cleanup()` вызывался из панели и удалял всё одним `DELETE`: юзер,
открывший статистику, ждал удаления десятков тысяч строк (вплоть до таймаута
PHP), а `DELETE` держал блокировки InnoDB и конфликтовал с импортом, который
пишет в ту же таблицу. Теперь функция выходит сразу, если вызвана не из CLI, а
крон удаляет пачками по 5000 строк, максимум 20 пачек за заход.

**4. Кэш офферов не затирается пустым списком.** `offers.php` — единственный
источник ссылок для go.php. Если база вернёт 0 кампаний (сбой, пустая или
подменённая база, недокачанный дамп), крон НЕ перезапишет файл: иначе все рефки
начали бы отдавать 404, причём тихо. Вместо этого в вывод крона попадает
предупреждение, а редиректы продолжают работать на прежнем кэше. Из панели
пустой список по-прежнему допустим — там это осознанное действие человека.

Что проверено end-to-end (реальный HTTP-сервер + CLI-крон):

| проверка | результат |
|---|---|
| редирект рефки | `302` с дописанным `clickid` |
| несуществующий слаг | `404` |
| запись клика в `clicks.log` | строка с IP, source, страной, clickid |
| постбек реги / депа | `OK` / `OK` |
| постбек с чужим ключом | `403` |
| крон: импорт + досвязывание | клики в базе, `досвязано конверсий: 2` |
| крон при занятом lock | выходит, `clicks.log` не тронут |
| крон при пустой базе | `offers.php` сохранён, рефка отдаёт `302` |
| очистка 12000 старых кликов | пачками, свежие целы, повторный вызов за сутки = 0 |

Отдельно: **go.php не подключает db.php вообще** — он читает только `config.php`
и `offers.php`. Ни кэш, ни MySQL, ни блокировки на отдачу рефок влиять не могут
по построению.

## Важные детали

- **offers.php обновляется автоматически** при изменении оффера в панели
  (add_campaign, update_offer, replace_offer_domain, delete_campaign).
  Плюс import.php обновляет его каждые 5 минут на всякий случай.
- **clickid** генерится в go.php и пишется в лог → попадает в MySQL при импорте.
  Привязка постбеков работает как раньше.
- **Уники/статистика** в панели — с задержкой до 5 минут (пока крон не импортнул).
- **Ботов** go.php помечает грубо (по UA). Точность та же, что была.
- **Флуд-лимит** сейчас не в go.php (убран, чтобы не читать состояние). Защита от
  флуда — на Cloudflare (rate limit правило). Это правильнее — режется на периметре.

## Обслуживание

- Файл `clicks.log` между импортами маленький (5 минут кликов). После импорта
  удаляется. Расти не должен.
- Если крон отвалится надолго — лог вырастет, но не потеряется. Проверяй, что
  крон работает (в панели статистика обновляется — значит импорт идёт).
- Логи import.php можно смотреть, запустив вручную:
  `https://sitegrator.com/import.php?key=СЕКРЕТ` — покажет, сколько импортнул.
