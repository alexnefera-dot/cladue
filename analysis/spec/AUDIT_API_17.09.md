# Аудит Analytics Export API — 17.09

Закрывает открытый пункт «Аудит API» из `PEREDACHA_API.md` §8. Хост доступен,
окружение `dorgen` работает. Всё ниже измерено, а не предположено.

Метод: `/v1/subdomains` с `date_field=pipeline_started`, по одной странице на каждую
дату 09–17.09 (по 200–300 строк), плюс страница в 1000 строк за окно 11–17.09.
Итого 125 полей в ответе.

## 1 · Три критичных поля — есть все три

Главный вопрос аудита снят.

| поле из §3 | статус | заполненность | разнообразие |
|------------|--------|---------------|--------------|
| `brand_id` | **есть** | 100% на всех девяти датах | 206 уник. на 1000 строк |
| `ya_account_id` | **есть** | 100% на всех девяти датах | 5 уник. внутри когорты |
| `cloudflare_account_id` | **поля с таким именем нет** | — | — |

Обязательные тоже на месте, 100% на всех датах: `subdomain`, `content_domain_id`,

**Единственное, что нужно подтвердить разработчику:** что `cf_account_id` — это
именно номер аккаунта Cloudflare, а не внутренний id строки. Если да, гипотеза
про эффект кластера проверяема.

Скрипт `pull_api.py` искал `cloudflare_account_id` и печатал ложное «НЕТ» —
исправлено в этом же коммите.

## 2 · БЛОКЕР: `/v1/subdomains` отдаёт 500 примерно на половине запросов

Это важнее всех недостающих полей: в таком виде массовая выгрузка нереальна.

Один и тот же запрос, восемь раз подряд с паузой 2.1 с:

| эндпоинт | коды | доля ошибок |
|----------|------|-------------|
| `/v1/subdomains` 15.09 limit=50 | 6×500, 2×200 | **75%** |
| `/v1/subdomains` 10.09 limit=50 | 4×500, 4×200 | **50%** |
| `/v1/traffic` 15–16.09 limit=50 | 3×500, 5×200 | 37% |
| `/v1/events` 16.09 limit=50 | 2×500, 6×200 | 25% |
| `/v1/globals` 15.09 | 8×200 | 0% |

Тело ответа: `{"error":{"code":"internal","message":"Internal error"}}`, HTTP 500.

**Ошибка не детерминирована и ни от чего не зависит.** Пять одинаковых запросов
подряд дали `200, 200, 500, 500, 500`. Проверено отдельно, что это не параметры:

- `limit=50` → 500, тот же `limit=300` → 200 (та же дата, тот же `date_field`);
- `date_field=pipeline_started` → 500, `cd_created` → 200;
- окно в один день → 500, окно в три дня → 500.

Чем «тяжелее» эндпоинт, тем чаще падает: `globals` (один объект) не падает никогда,
`events` 25%, `subdomains` 75%. Похоже на таймаут или исчерпание ресурса в
обработчике, а не на логику.

**Что просим:** найти причину по серверным логам за 17.09. Для нас практический
критерий — курсорная выгрузка на сотню страниц должна проходить без ретраев.
Сейчас при 50% на запрос выгрузка недели рвётся гарантированно.

## 2-бис · БЛОКЕР: `/v1/traffic` отдаёт курсор, который сам же не принимает

Найдено 17.09 при первой же реальной выгрузке недели. Эндпоинт непригоден дальше
первой страницы.

```
страница 1: 1000 строк, next_cursor выдан
тот же запрос + этот cursor  ->  400 {"error":{"code":"invalid_param",
                                     "message":"invalid cursor"}}
```

Проверено, что дело не в наборе параметров и не в нашей стороне — перебраны все
варианты, и ни один не проходит:

| запрос на вторую страницу | `/v1/traffic` | `/v1/events` | `/v1/subdomains` |
|---|---|---|---|
| те же параметры + `cursor` | **400 invalid cursor** | 200 | 200 |
| `cursor` + даты, без `limit` | **400 invalid cursor** | 200 | 200 |
| те же параметры + `cursor`, `limit=500` | **400 invalid cursor** | 200 | 200 |
| только `cursor` | 400 нужны даты | 400 нужны даты | 400 нужны даты |

Причина видна в самом курсоре — у `traffic` он другой формы:

```
traffic      {"d":"2026-09-11",…      <- по дате
events       {"id":1821129}           <- по id, работает
subdomains   {"id":220841}            <- по id, работает
```

**Обхода нет.** Нарезка по дням не спасает: каждый день 11–17.09 упирается ровно в
1000 строк и просит курсор, то есть ни один день не влезает в одну страницу.
Фильтр `subdomain` из спеки означал бы 28 тысяч запросов на день — 16 часов, не
вариант. Итог: из `/v1/traffic` сейчас извлекаемы ровно первые 1000 строк на любой
запрос, всё остальное недостижимо.

**Что это стоит анализу.** `clicks` и `views` по дням — это правило 7 (экспозиция
в домен·днях) и кривая видимости из §7 передачи. Суммы `clicks_sum` / `views_sum`
в `/v1/subdomains` есть, но они без разбивки по датам, а вся работа по времени
прихода робота строится именно на ней.

**Что просим:** чинить курсор `/v1/traffic` — судя по форме, он собирается по дате,
а разбирается как id. Это приоритет 1 вместе с пятисотками.

## 3 · ЗАЯВКА: `content_label` отсутствует у 286 баз из 752

Правило 5 рабочего мануала — «контент это один параметр, целиком имя». Для
38% баз недели этого параметра через API нет.

**Уточнение к первой редакции этого отчёта.** Сначала цифры брались из выборок по
200–300 строк на дату, и по ним выходило, что 14.09 пуст целиком. Полная выгрузка
недели (154 800 строк) показала, что на 14.09 заполнено 56%, а граница проходит не
по датам, а **по базам**. Ниже — числа по всем данным, а не по выборке.

Заполненность `content_label` по дате старта пайплайна, полные данные:

| дата | строк | с контентом | баз без контента |
|------|-------|-------------|------------------|
| 11.09 | 24 514 | 0% | 119 |
| 12.09 | 20 806 | 0% | 101 |
| 13.09 | 7 210 | 0% | 35 |
| 14.09 | 14 832 | **56%** | 31 |
| 15.09 | 32 960 | 100% | 0 |
| 16.09 | 28 110 | 100% | 0 |
| 17.09 | 26 368 | 100% | 0 |

**Признак живёт на уровне базы, а не строки.** Из 752 баз недели 466 заполнены
полностью и 286 пусты полностью. Смешанных — **ноль**. То есть это не потеря
отдельных записей, а отсутствие связи «база → контент» для конкретных баз.

**И это не просто «фичу включили 14.09».** Внутри 14.09 первая база с контентом
стартовала в 16:38, но пять баз, стартовавших заметно позже — 1471 в 17:02,
1460 в 17:41, 1468 в 18:33, 1458 в 19:17, 1450 в 19:47 — контента не имеют.
При этом все базы 14.09 созданы в одни и те же две минуты (00:34:06 и 00:37:41),
так что ни время старта, ни время создания базы границу не объясняют.

Вместе с `content_label` у тех же баз пусты `content_id`, `pack_kind`,
`title_ru_len`, `description_ru_len`, `additional_text_ru_len`,
`additional_text_2_ru_len`, `generation_runs_count`. `content_domain_id` при этом
заполнен на 100% везде — идентификатор базы есть, нет привязанного к нему контента.

**Почему это дорого.** Установленный результат по семействам контентов (NEW102
1.82× от среднего, `nabory` 0.37× при нуле ФД на 188 доменах, χ²=23.4, p≈0.0015)
посчитан по `analysis/launch_*.txt`, а не по API. Через API его не воспроизвести:
52 530 строк за 11–14.09 идут без имени контента. Любой анализ контента в
контролируемом по возрасту окне (правило 9) упирается в эти четыре дня.

**Что просим:** проставить `content_label` и `content_id` для 286 баз — список
с id, доменом и временем старта лежит в `analysis/spec/content_label_propusheno.txt`. Важнее общего ответа — объяснение,
почему пять баз 14.09, стартовавших после перехода, остались без связи: если это
можно повторить, то дыра появится и в будущих данных. Если исторической связи в БД
нет вовсе — сказать прямо, тогда мы закрываем это навсегда и считаем контент
только по своему реестру.

**Отдельно:** `oform_version` заполнен 15–16.09 и снова пуст 17.09. Либо регрессия,
либо поле перестали писать — нужен ответ, что из двух.

## 4 · ЗАЯВКА: `quota_wait_until` пуст, хотя значение есть в тексте рядом

На 17.09 поле `pipeline_error` заполнено у 100% строк, но это **не ошибка**:

```
"150 готово, 56 ждут квоту (до 18.09.2026 10:46 Киев)"   — 102 строки
"150 готово, 56 ждут квоту (до 18.09.2026 10:34 Киев)"   —  97 строк
"Суточная квота переобхода исчерпана"                    —   1 строка
```

Для сравнения, 16.09: `pipeline_error = null` у всех 200 строк.

Две проблемы сразу:

1. **`quota_wait_until` = `null` у 100% строк во всех когортах**, хотя время
   ожидания напечатано прямо в тексте `pipeline_error`. Значение существует —
   его просто не кладут в поле. Это самая дешёвая правка из всего списка.
2. **`pipeline_error` используется как поле статуса, а не ошибки.** Отличить
   настоящий сбой от «ждём квоту» можно только разбором русской строки. Просим
   либо отдельное поле статуса, либо машинный код вместо текста.

`yandex_pipeline_stage` при этом различает состояния корректно (`done` 199,
`quota_wait` 1) — но не совпадает с `pipeline_error`, который заполнен у всех 200.

Приоритет для нас: `quota_wait_until` (см. §4), затем `had_hosts_purge` и

намеренных `null`, если отдавать не планируется.

Отдельно странно, что `title_ru_len` и `description_ru_len` отдаются, а `h1_len`
и `page_body_len` — нет, хотя это метрики той же страницы.
