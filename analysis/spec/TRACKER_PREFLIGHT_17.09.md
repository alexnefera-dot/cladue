# Трекер: проверка перед подключением, 17.09

Второй источник — API трекера `sitegrator.com`, эндпоинты `/v1/clicks` и
`/v1/conversions`. Контракт: `API.md` в ветке `claude/sitegrator-redirector`.
Конверсии и клики берутся оттуда напрямую, CSV больше не нужен.

Ниже — то, что удалось проверить **до** получения доступа, по уже выгруженным
данным запусков и по старому CSV. Ключ соединения проверен на реальных строках,
а не принят на веру.

## 1 · Состояние доступа

| | |
|---|---|
| сеть до `sitegrator.com` | **открыта** — приходит `401` от самого API, а не `403` от прокси |
| формат ошибок | совпадает с dorgen: `{"error":{"code":"unauthorized",…}}` |
| `TRACKER_BASE` / `TRACKER_TOKEN` | **в сессии отсутствуют**, есть только `DORGEN_*` |

Переменные окружения подставляются при старте контейнера, поэтому добавленные
позже в текущую сессию не попадают — нужна новая сессия в окружении `dorgen`.
Токен в переписку не передавать: по §2 передачи он живёт только в переменных
окружения.

Проверка после перезапуска:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TRACKER_TOKEN" \
  "$TRACKER_BASE/v1/conversions?date_from=2026-09-10&date_to=2026-09-17&limit=2"   # ждём 200
```

### Cloudflare режет Python по User-Agent

Найдено при первом же вызове скрипта. Перед `sitegrator.com` стоит Cloudflare, и
он отвечает **403 Error 1010** на User-Agent вида `Python-urllib/*`:

| клиент | ответ |
|---|---|
| `curl` со своим UA | 401 (нормальный ответ API) |
| `curl -A "Python-urllib/3.11"` | **403 Cloudflare** |
| `urllib` без UA (шлёт `Python-urllib/3.11`) | **403 Cloudflare** |
| `urllib` с `User-Agent: cladue-analytics/1.0` | 401 (нормальный ответ API) |
| dorgen, `urllib` без UA | 200 — такого правила нет |

Поэтому `pull_tracker.py` шлёт явный `User-Agent`. Без него выгрузка упала бы на
первом запросе после получения токена, причём с ошибкой Cloudflare, которая ни
на что осмысленное не указывает.

## 2 · Ключ соединения работает, но 2% строк отравлены

Проверено на `analysis/konversii_7dney.csv` (164 конверсии 09–16.09) против
выгрузки `/v1/subdomains` за 11–17.09 (154 800 сабдоменов).

| | |
|---|---|
| конверсий с пустым ключом | **0 из 164** |
| уникальных сабдоменов в конверсиях | 132 |
| правдоподобный ключ (в выгрузке или в реестре доменов) | **160 из 164 (97%)** |
| ключ не опознан | 4 |

Из 74 сабдоменов, которых нет в выгрузке 11–17.09, **66 прослеживаются в
`launch_*.txt` за 24.08–10.09** — то есть это не поломка ключа, а запуски раньше
окна выгрузки. Соединение по `subdomain` состоятельно.

### Четыре отравленные строки — это подстановка хоста реферера

| `source` | `referer` |
|---|---|
| `arkadaclubplay.buzz` | `https://arkadaclubplay.buzz/` |
| `lelang.su` | `https://lelang.su/` |
| `yandex.com` | `https://yandex.com/images/sear…` |
| `pinco.jkrv.team` | `https://duckduckgo.com/` |

В первых трёх `source` **дословно равен хосту реферера**. Это ровно тот отказ,
который описан в контракте: без параметра `site=` трекер берёт `subdomain` из
хоста реферера. Значит подстановка не гипотетическая — она происходит и даёт
ключ, которого в нашей сети не существует (`yandex.com`, зона `.su`).

Четвёртая строка иная: `pinco.jkrv.team` по форме нормальный сабдомен, но
`jkrv.team` нет в реестре из 1864 доменов, а реферер — DuckDuckGo.

**Правило при подключении.** Строки, чей `subdomain` не найден ни в выгрузке
`/v1/subdomains`, ни в `domains_flat.txt`, в расчёт не брать. Но **не отбрасывать
молча** — считать и показывать их числом: рост этой доли означает, что дор
перестал передавать `site=`, и это надо заметить сразу, а не через месяц.
Признак отравления: `subdomain` равен хосту `referer`.

## 3 · Что проверить первым делом, когда появится доступ

1. **Доля кликов с `subdomain: null`.** Контракт предупреждает, что без `site=`
   такие клики выпадают из соединения. Отдельно тревожно вот что: сказано, что
   реферером служит Яндекс или пусто, потому что дор редиректит на сервере —
   значит подстановка из реферера в принципе не может дать наш сабдомен. По
   старым конверсиям ключ всё же заполнен у 100% строк, то есть `site=`
   передаётся; но у кликов доля может быть другой, и это первое число, которое
   надо увидеть.
2. **`is_bot`.** Боты не отфильтрованы. Правило 6 мануала — клики это факт, а не
   фактор; долю ботов посчитать и показать, молча не выбрасывать.
3. **Окно по `meta.stable_until`.** Брать только полностью устоявшийся период,
   иначе свежие конверсии придут с пустым `subdomain` и `linked_at`.
4. **`landing_path`** пока `null` — дор не передаёт `lp=`, правка на его стороне
   в работе. До неё глубина входа не считается.
5. **`payout` и `status`** всегда `null`: суммы и отмены партнёрка не шлёт.
   Экономику на них не строить.
6. **`retention_days`.** `/v1/clicks` за период старше retention вернёт пусто.
   Узнать значение до того, как планировать историю глубже недели.

## 4 · Замечание о ссылках дора

Во всех 154 800 строках выгрузки `ref_link_host` = `sitegrator.com`, а
`ref_link_slug` содержит только путь (`/go/dorgen_engine` у 135 252 строк, всего
27 вариантов) — без `site=` и без `lp=`. Само по себе это не доказывает, что
движок их не шлёт: поле похоже на хранимый слаг без query-части, а конверсии
показывают, что `site=` до трекера доходит. Но проверить по живым кликам стоит
(пункт 1 выше).
