# yandex-sites

Инструмент на PHP, который прогоняет список поисковых запросов через выдачу
Яндекса, собирает сайты из результатов, отбирает нужные по настраиваемым
правилам и, при желании, заходит на каждый отобранный сайт как посетитель из
поиска, сохраняя HTML и скриншоты страниц.

Что умеет:

- **веб‑интерфейс** (окно в браузере): ввод ключей, запуск сбора, прогресс, таблица
  результатов и повтор сбора по таймеру — без работы в консоли;
- три источника выдачи: официальный **Yandex Search API**, сервис **XMLStock**
  (Яндекс.XML или живая выдача Яндекса — на выбор) и **живая выдача** yandex.ru,
  как её видит обычный пользователь (через ваши прокси);
- отбор сайтов: доменные зоны, чёрные и белые списки доменов, слова и
  регулярные выражения в заголовке и сниппете, регулярные выражения по URL,
  минимальное число запросов, в выдаче которых встретился сайт;
- HTTP-проверка сайтов: код ответа, редиректы на чужой домен, наличие или
  отсутствие текста на странице (телефон, «домен продаётся»);
- визиты на сайты через headless Chromium (Playwright) или curl с Referer
  выдачи Яндекса; несколько визитов на сайт с разными прокси и User-Agent,
  чтобы увидеть, показывает ли сайт разным посетителям разные версии страницы;
- результаты в `sites.csv` (открывается в Excel), `sites.json`, `domains.txt`,
  страницы сайтов в `out/pages/<сайт>/` (при обходе шапки — в `out/pages/<N>-стр/<сайт>/`,
  файлы названы по URL).

Ответы источников кэшируются: фильтры можно менять и перезапускать отбор без
повторных обращений к выдаче.

## Требования

- PHP 8.1 или новее с расширениями `curl`, `dom`, `json`, `mbstring`
  (`intl` желательно для кириллических доменов в фильтрах).
- Для визитов с выполнением JavaScript — Node.js 18+ и Playwright
  (`npm install playwright && npx playwright install chromium`); без них
  визиты выполняются через curl.
- Composer не обязателен: сторонних PHP-зависимостей нет, автозагрузка встроена.

## Установка

```bash
git clone https://github.com/alexnefera-dot/cladue.git
cd cladue
php bin/setup.php --proxy=http://host:port:user:pass
```

`bin/setup.php` создаёт `config.php`, `.env` и `proxies.txt` из примеров
(существующие файлы не трогает), добавляет переданные прокси, создаёт папки
`cache/`, `out/`, `debug/`, проверяет PHP-расширения и Playwright и печатает
команды для проверки прокси и пробного запуска. Обновить код до свежей версии
с GitHub, не трогая настройки, прокси, кэш и результаты: `php bin/setup.php --update`.
Все команды выполняются из папки проекта: сначала `cd` в неё (её путь панель показывает под заголовком —
«Папка проекта: …», и печатает при запуске в консоли), потом `php bin/setup.php --update` или `php bin/panel.php`.
После обновления **перезапустите панель** (Ctrl+C в её окне и снова `php bin/panel.php`) — запущенная
панель продолжает работать на старом коде. Как убедиться, что стоит новая сборка: команда обновления
печатает «версия yandex-sites X.Y.Z от ДД.ММ.ГГГГ», та же версия и дата видны в шапке панели рядом с
названием (обновите страницу) и в консоли по `php bin/yandex-sites.php --version` — они должны совпадать.
Прошлый сбор при обновлении не пропадает, а то, что новая версия умеет считать по уже сохранённым
страницам (например, тип вёрстки), она досчитывает на прошлом списке сама — новый сбор не нужен.
Всё то же можно сделать руками:

```bash
cp config.example.php config.php   # источник, правила отбора, визиты
cp .env.example .env               # данные доступа к API / XMLStock
cp proxies.example.txt proxies.txt # прокси для живой выдачи и визитов
```

## Веб‑интерфейс

Кто не хочет работать в консоли — запустите панель управления, она откроется в браузере:

```bash
php bin/panel.php
```

Панель (адрес `http://127.0.0.1:8777`, доступна только с этого компьютера) разбита на три
вкладки: **«Главная»** (запросы, запуск, прогресс, журнал и таблица результатов),
**«Настройки»** (ключи доступа и все условия отбора) и **«Статистика»** (история сборов: что и
когда собрано, сколько доров, их доля, повторы доров и зоны доров). Панель позволяет:

- ввести ключи доступа (XMLStock, при желании Yandex API) — они сохраняются в `.env`;
- задать запросы и условия отбора: источник, регион, число страниц, разрешённые зоны,
  дополнительные исключения доменов;
- **параметры XMLStock** (когда выбран этот источник): тип выдачи — **Яндекс.XML** (до 100
  сайтов на странице, дешевле) или **живая выдача** (как у пользователя, по 10 сайтов на
  странице: «топ 30» = 3 запроса), устройство выдачи (мобайл / десктоп / планшет), домен Яндекса
  (`yandex.ru` / `.by` / `.kz` / …) и произвольные доп. параметры (`key=value` через `&`,
  например `within=77`);
- **дедупликация по домену** — «один сайт на домен»: если домен уже есть, любой его
  поддомен второй раз не берётся (это же можно включить в конфиге как `unique_by => 'domain'`);
- **тип домена** — брать любые домены, только корневые (`example.ru`) или только поддомены
  (`shop.example.ru`) (`filters.domain_scope`);
- включить открытие найденных сайтов в браузере (Chromium) с числом заходов и движком;
- **брать только топ N выдачи** (по умолчанию 10);
- **чего не хватает (ключевые страницы)**: контент ссылается на регистрацию, вход, зеркало, бонусы,
  приложение и слоты, поэтому пропущенная страница превращается в «ссылку в никуда». После выгрузки
  видно, чего не хватает: в строке сайта — метка **«нет: регистрация, зеркало»**, над таблицей —
  **«не хватает страниц у N сайтов: регистрация — 213, вход — 115…»** (та же строка в сообщении задания
  и в журнале). Дальше два пути: кнопка **«Добрать ключевые (N)»** — страницы с ошибкой перекачиваются,
  а те, ссылки на которые не нашлось в меню, пробуются по стандартному адресу (`/registracia`, `/vhod`…);
  если такой страницы у сайта нет, ответ 404 просто не сохранится и счётчик страниц не испортит. Или
  выбрать нужную страницу в списке **«нет страницы: …»** и нажать **«Убрать»** — сайты без неё уйдут из
  таблицы (обратимо, «вернуть все»). Список **«нет страницы»** появляется только **после выгрузки
  страниц**: пока открыта одна главная, меню никто не обходил и «нет регистрации» верно про любой сайт —
  раньше этот фильтр сразу после сбора выбирал весь список, и одно нажатие «Убрать» очищало таблицу;
- **технический разбор выдачи** (отдельная страница, ссылка «Разбор выдачи ↗» в шапке панели): выдача
  **как она есть** — блок на каждый бренд, внутри все его ключи со своим топом, **ничего не склеено и
  не выброшено**. Видно всё, что главная отсеяла (у каждой строки написана причина) и что она свела в
  один сайт. **Цветом подсвечены пересечения**: жёлтым — сайт, который встретился в нескольких ключах
  одного бренда, сиреневым — сайт, который держится сразу на нескольких брендах (это сетка). В конце
  каждого бренда — сколько каких сайтов: **доры, тематические домены, соцсети, известные сайты рунета,
  прочие**. Все числа — **по разным сайтам**: домен, который стоит на нескольких брендах, в общем итоге
  считается один раз, а разница между суммой по брендам и общим итогом показана отдельной строкой —
  это и есть **повторы между брендами**. У каждого дора видно, **наш он или чужой** (по меткам наших
  шаблонов и по накопленному списку наших доменов), в шапке бренда — «наших доров N», в сводке — сколько
  наших доров всего **и почему**: «метка «faro» — 120 · домен в списке наших — 18», рядом сами
  действующие метки. Наведите на метку «наш» у сайта — покажет причину именно для него. Метка сверяется
  **только с адресом сайта**, а не со страницей: раньше чужой `site.top/faro-bonus` попадал в «наши». Бренды можно **сортировать** (по дорам, по нашим дорам, по сайтам, по ключам, по
  пересечениям, по сайтам на нескольких брендах, по изменениям) и **фильтровать** («только с дорами»,
  «только с нашими», «с дорами, но без наших», «только изменившиеся» …), чтобы смотреть только нужное.
  После пересбора в блоке бренда появляется **что изменилось**: сколько сайтов добавилось и
  сколько пропало, с разбивкой по типу и списком адресов. Главная страница и весь сбор при этом не
  меняются — разбор строится из тех же результатов сбора;
- **наши домены из системы запусков (dorgen)**: самый точный ответ на вопрос «наш ли это сайт» —
  список приходит от самой системы, а не угадывается по меткам. Впишите в `.env` рядом с проектом
  `DORGEN_TOKEN` (образец — `.env.example`), и на странице «Разбор выдачи» кнопка **«Обновить наши
  домены»** догрузит наши запущенные поддомены. Сверка идёт по **базе** — последним двум меткам адреса
  (`leebet.4916.team` → `4916.team`): каждая база несёт все бренды, поэтому множества баз достаточно.
  Выгрузка **догружает только новые дни** (кэш помнит, по какой день уже выгружено), сам сырой ответ не
  хранится — только базы. Из консоли то же самое: `php bin/dorgen-sync.php` (или `--from=…`, `--to=…`,
  `--days=7`, `--list`). Метки наших шаблонов и список `own-domains.txt` продолжают работать как раньше;
- **выгрузка частями (волнами)**: страницы качаются не «весь список разом», а волнами по
  **«Сайтов в волне»** (в «Настройках», по умолчанию 50). Обход устроен по этапам — сначала главные
  всех сайтов, потом пробные, потом остальные страницы, — поэтому без волн ни один сайт не считается
  готовым до самого конца, и работать было не с чем. После каждой волны её сайты **сразу** появляются
  в таблице и в `sites.json`, а с галочкой **«Чистить контент сразу после каждой волны»** тут же
  чистятся — готовые статьи ложатся в `content/` по ходу дела. В строке прогресса видно
  «готово 120 из 600 (волна 3 из 12)». Кнопка «Остановить» срабатывает **между волнами**: уже
  выгруженные части остаются на диске, а сайты, до которых не дошли, сохраняют прежние превью;
- **архив контента по частям**: рядом с «Очистить всё» — две кнопки. **«Скачать всё (N стр.)»** отдаёт
  весь очищенный контент, **«Скачать новое (N стр.)»** — только те статьи, которых не было в прошлых
  архивах (файл `content-part-2-2026-09-25.zip`). То есть вторая волна приедет **без первой части**, и
  ничего не нужно разбирать руками. Отметки ставятся по содержимому статьи, поэтому повторная
  «Очистить всё» не превращает весь архив снова в «новое». Ссылка **«считать всё новым»** сбрасывает
  отметки (статьи на диске остаются), а новый сбор обнуляет их вместе с прежним контентом;
- **скорость (потоки)**: три поля в «Настройках» — **«Запросов выдачи разом»** (по умолчанию 5),
  **«Страниц разом»** (4) и **«Браузеров разом»** (2). Раньше всё шло строго по одному: 3000 запросов
  к источнику друг за другом, страницы сайтов — по две с паузой 1,5 с, а браузеры (по одному на прокси)
  запускались по очереди, так что лишние прокси ничего не ускоряли. Теперь выдача тянется пачками
  параллельно (лишних обращений к источнику не появляется — вторая страница запрашивается только там,
  где первая была полной), браузеры работают одновременно, а пауза между заходами считается отдельно
  для каждого прокси и каждого сайта. Всего страниц в работе — «браузеров × страниц», каждый браузер
  это ещё 200–300 МБ памяти. Чем больше прокси в `proxies.txt`, тем смелее можно поднимать значения;
  если источник начнёт отвечать ошибкой лимита, уменьшите «Запросов выдачи разом». На живую выдачу
  через прокси потоки не влияют — там по-прежнему строгий порядок и паузы;
- **сбор частями (большой список ключей)**: не нужно ждать все 3000 запросов. Сбор идёт, пока вы не
  нажмёте **«Остановить»** — остановка **мягкая**: задание доводит текущий запрос, сохраняет собранные
  сайты и запоминает позицию в списке (`runs/current/queue.json`). С этой частью сразу можно работать:
  убрать лишние сайты, оставить нужный тип вёрстки, выгрузить страницы и очистить контент. Потом кнопка
  **«Продолжить сбор (N)»** рядом с «Собрать сайты» запускает остаток запросов и спрашивает, что делать с
  уже собранными сайтами в таблице: **«Оставить»** (новые добавятся к текущим) или **«Очистить таблицу»**
  (в таблице будут только сайты новой части — удобно, когда предыдущую вы уже обработали). Выгруженные
  страницы и очищенный контент на диске при этом не трогаются: выгрузка и очистка теперь работают
  **только по сайтам из таблицы**, поэтому предыдущие части остаются в `runs/current/pages` и
  `content` в целости. Под кнопками видно «Запросы списка: пройдено N из M, осталось K». Если задание
  зависло, рядом появляется **«Прервать принудительно»** (собранное с момента последнего сохранения
  теряется). **«Собрать сайты» всегда начинает всё заново**: список запросов проходится с начала, а
  результаты прошлого прогона удаляются — выгруженные страницы (`pages`), очищенный контент
  (`content`), превью и готовый архив `content.zip`. Иначе после очистки новые статьи ложились бы к
  старым и архив приходил вперемешку с сайтами прошлого сбора. Панель предупреждает и называет,
  сколько сайтов и статей пропадёт, — если архив ещё нужен, скачайте его перед новым сбором;
  «Продолжить сбор» ничего не удаляет;
- **дубли запросов по выдаче**: после сбора под списком запросов панель показывает, сколько запросов
  дали ту же выдачу, что и другой запрос (совпал **набор сайтов**, позиции не важны), и кнопкой
  **«Убрать дубли из списка»** удаляет их из списка запросов (в каждой группе остаётся первый по списку);
  рядом ссылки «список без дублей» (`runs/current/queries-unique.txt`) и «группы дублей»
  (`query-dupes.txt`). Считается по `results.csv` последнего сбора — работает и для сбора, сделанного до
  обновления; запросы без результатов дублями не считаются, их число показывается отдельно;
- **база собранных доменов**: каждый сбор записывает найденные домены в общую базу
  (`runs/domains-base.txt`) и по умолчанию **пропускает пересечения** — домены, которые
  уже собраны раньше, второй раз не берутся; базу видно в панели. Ссылка **«очистить базу и файлы»**
  рядом с ней — полный сброс: очищается база доменов И удаляются все рабочие файлы прогона (скачанные
  страницы `pages`, очищенный контент `content`, превью, списки сайтов, очередь запросов). **Статистика
  сборов при этом не трогается** — это летопись, её чистит отдельная ссылка рядом:
  **«очистить статистику»** удаляет только историю со вкладки «Статистика», а база доменов, страницы и
  контент остаются на месте. Итоговый
  архив контента скачивается через панель заранее, поэтому эти папки технические; запросы и настройки
  остаются, следующий сбор начинается с чистого листа (во время работы задания сброс не выполняется —
  сначала остановите его). Поэтому
  повторный сбор по тем же запросам честно говорит «Ничего нового: N доменов уже в базе» — снимите
  галочку «Пропускать домены…» или очистите базу, чтобы отобрать эти домены снова;
- **понятные числа в прогрессе**: на «Главной» во время сбора идёт воронка, где каждое число вытекает из
  предыдущего — **запросов** → **результатов в выдаче** (все строки по всем запросам: один сайт считается
  заново в каждом запросе, где он попался) → **сайтов в выдаче** (вся масса, сведённая по правилу «один
  сайт на домен»: поддомены одного домена — доры одной сетки — это один сайт; число разных адресов
  показывается в подсказке, отдельной карточкой оно только путало) → **отобрано сайтов** (после фильтров)
  → и, если отличается, **из них новых в базу**. У каждой карточки подсказка при наведении. «Отобрано» —
  это результат фильтров, а **не** «сайт открылся»: заходим мы на них позже, и это видно в строке над
  таблицей результатов. Строка **«Отсеяно (по строкам выдачи)»** под карточками считает фильтры выдачи по
  строкам, а «уже в базе» и «мало запросов» — по сайтам, поэтому складывать её с воронкой нельзя: тот же
  отсев, посчитанный по сайтам, лежит во вкладке «Статистика» в колонке **«Срезано»**;
- **проблемные сайты прямо в таблице результатов** — те, которые **не удалось получить** (а не те,
  у которых чего-то нет). Причина привязана к **стадии**, а не сваливается кучей после скриншотов:
  **по сбору** видно сразу после сбора со скриншотами (сайт вообще не открылся — «не открылся»; или
  показал **витрину чужих офферов** вместо себя), **по выгрузке** — после «Выгрузить страницы»
  (ни одной страницы не выгрузилось; часть страниц упала так, что докачка их доберёт; файл открытой
  страницы пропал с диска). **Не** проблема: одностраничник (после выгрузки открылась только главная
  и больше страниц нет), пропуск целевой страницы (её просто нет — это не сбой загрузки), а также 404
  и дубликаты — такие сайты считаются отдельно, «частично (404/дубли)». У каждой строки таблицы —
  красная метка с причиной, а над таблицей выбор **«проблемные: [причина]»**: он сужает таблицу до
  выбранной причины, и рядом появляются кнопки **«Перепробовать с других IP»** (ещё заходы на главную
  с других прокси и браузерных агентов — для сайтов, которые ещё не выгружались), **«Докачать»**
  (для выгруженных) и **«Убрать (N)»** (обратимо, «вернуть все»). На выгрузку и «Очистить всё» фильтр
  не влияет — они всегда берут все оставшиеся сайты. Число проблемных совпадает со строкой статистики
  над таблицей, дублируется в сообщении сбора/выгрузки и в журнале с разбивкой по стадиям.
- **вкладка «Статистика»** — история сборов, всё про **доры**, и это **сходящаяся воронка**. Сверху —
  сама воронка, шаг за шагом, с процентом на каждом шаге: **результатов в выдаче** → **адресов в выдаче**
  (% от строк) → **сайтов в выдаче** (% от адресов) → из них **доров** (а под ними — сколько доров
  **наших**) и **корневых** (% от сайтов) → **срезано фильтрами** с разбивкой по причинам (у каждой —
  % от сайтов выдачи и сколько среди них доров) → **отобрано сайтов** (% от сайтов выдачи) → из них
  **доров** и **доменов с 6+ брендами** (% от отобранного).
  Первый блок считается от строк выдачи, второй — от сайтов выдачи, и каждый блок это подписывает.
  **Наши шаблоны** стоят строкой под дорами, и доля считается **от общего числа доров в выдаче**: наши
  сайты и есть доры, так что вопрос «сколько доров в нише наши» отвечается только так. В число входят и
  те, что пришли **повторами** — домен уже в базе пересечений, сайт мы даже не открываем, но в выдаче он
  стоит и он наш, — и те, что **срезаны по метке-домену** (их мы не собираем вовсе). Чтобы это работало,
  свои домены запоминаются между сборами в `runs/own-domains.txt` (очищается вместе с базой кнопкой
  «очистить базу и файлы»), список сам достраивается по прошлым сборам на диске, а домены, собранные
  ещё раньше, можно вписать руками в **`own-domains.txt`** в корне проекта.
  **Домены с 6+ брендами** — те, что держат на своих поддоменах сайты **более чем пяти разных брендов**:
  это площадка сетки, а не обычный сайт. Бренд берётся из поискового запроса, которым сайт нашёлся, и
  написания сводятся к одному: «Вулкан Вегас» и «Vulkan Vegas» — один бренд, «Криптобосс» и
  «Cryptoboss» — тоже. Считаются только доры (адреса на поддоменах) среди **отобранных** сайтов, поэтому
  сайт-обзорник, который ранжируется по шести брендовым ключам со своего домена, в список не попадёт.
  Полный список с названиями брендов пишется в `runs/current/brand-domains.txt` и скачивается ссылкой
  **«домены с 6+ брендами»** под таблицей результатов. Пары написаний берутся из встроенного списка (166 брендов);
  свои можно дописать в `brand-pairs.txt` рядом с проектом — строка латиницей, следом строка кириллицей.
  Выпадающий список над воронкой переключает её между **любым сбором** и **итогом за всё время**; клик
  по строке таблицы внизу показывает воронку этого сбора. Ниже воронки — зоны доров и размер базы.
  Таблица — по строке на каждый сбор, новые сверху, теми же понятиями, что и на «Главной». В строке — **дата и
  время**, сколько было **результатов в выдаче**, сколько это **сайтов в выдаче** — вся масса, сведённая
  по правилу «один сайт на домен» (в подсказке — сколько это было разных адресов), сколько из них
  **доров** (сайтов на поддоменах, `kush.casinozsd.buzz` при `casinozsd.buzz`) и какая это **доля**,
  сколько **срезано** фильтрами (в подсказке — разбивка по причинам: «не тот тип домена — 3 200
  (доров 2 100); уже в базе доменов — 1 185; зона домена не разрешена — 240»),
  сколько доменов **отобрано в базу** (в подсказке — сколько из них доров), сколько **наших
  шаблонов** (доля — от общего числа доров, см. ниже), сколько **доменов с 6+ брендами** (см. ниже), сколько **повторов-доров**
  отсеяно как уже собранные раньше (в подсказке — сколько повторов было всего) и **по каким доменным
  зонам разошлись доры** (`.casino — 1010`, `.buzz — 251`, …). Сходимость проверяемая:
  **сайтов в выдаче = отобрано + срезано**, так что на вопрос «куда делись домены» отвечает сама
  таблица. Фильтры выдачи (зона, тип домена, исключения, позиция, слова в заголовке и описании)
  считаются здесь **по сайтам**, а не по строкам выдачи; «уже в базе», «мало запросов» и «не ответил
  на проверку» срабатывают уже после группировки и тоже попадают в эту разбивку. Наш сайт узнаётся **не по картинке
  скриншота**, а по меткам в HTML страницы (`filters.own_markers` + `own-markers.txt`) — скриншот нужен
  только чтобы проверить глазами. **Наших считаем всех, кто стоит в выдаче**, тремя частями (видно в
  подсказке над числом): отобранные сейчас (метка нашлась на превью-визите) + пришедшие **повторами**
  (домен уже в базе пересечений, такой сайт мы даже не открываем) + **срезанные по метке-домену** (их
  мы не собираем вовсе). Доля — от **общего числа доров выдачи**: наши шаблоны и есть доры, а считать
  её от отобранного смысла нет — если фильтр «тип домена» оставляет только поддомены, там всегда будет
  под 100%. Чтобы узнать своих среди повторов, нужен список своих доменов: он копится сам
  (`runs/own-domains.txt` — туда попадает каждый сайт, помеченный нашим) и достраивается перед каждым
  запуском по тому, что помнит диск — строки «наш» в таблице, сайты, убранные кнопкой «Убрать наши», и
  папки `runs/current/pages/наши/`. Домены, собранные ещё раньше, на диске уже не лежат — их можно
  просто вписать в **`own-domains.txt`** в корне проекта (по одному в строке, поддомены учитываются
  сами); файл не коммитится и переживает обновление кода. Если список пуст, в журнале сбора так и
  сказано, а в подсказке к числу наших видно, сколько доменов в нём вообще известно. Зоны считаются
  **по найденным дорам**: зона корневого сайта про сетку ничего не говорит. Сверху —
  «За всё время» в списке над воронкой: те же шаги, но суммой по всем сборам (проценты пересчитываются
  из сумм, а не усредняются; размер базы берётся из самого свежего сбора). Строка сбора появляется **сразу, как только
  домены отобраны** — ждать обхода сайтов со скриншотами не нужно; в конце сбора она уточняется (визиты
  показывают редиректы на бренд-поддомены — это тоже доры, и тогда же становится известно, сколько
  среди отобранного наших шаблонов). Кнопка **«Скачать CSV»** отдаёт ту же
  таблицу для Excel. История лежит в `runs/history.json` (хранится 500 последних сборов) и переживает
  обновление кода; очищается **только** ссылкой **«очистить статистику»** в настройках — полный сброс
  «очистить базу и файлы» историю сборов сохраняет. Записи идут с версии
  1.10.0: прошлые сборы в ней не задним числом, а начиная со следующего. Число наших появилось в 1.15.0
  и в **последнюю** запись дописывается по текущей таблице при первом же открытии вкладки — новый сбор
  ради него не нужен. Так же и воронка (сайты выдачи + срезанное), добавленная в 1.16.0: она
  досчитывается для последнего сбора по его же `runs/current/results.csv`, если файл описывает именно
  этот сбор (сходятся число строк и число адресов); у сборов, шедших частями, и у записей, чей
  results.csv уже перезаписан, в колонке «Срезано» остаётся прочерк. Дор определяется по
  **настоящему адресу сайта** — по тому, что стоит в выдаче, а если главная редиректит (сетка часто
  собирается по апексу `casinozsd.buzz`, а он ведёт на бренд-поддомен `kush.casinozsd.buzz`), то по
  конечному адресу. Учтите: при включённой галочке «один сайт на домен» разные поддомены одного домена
  сводятся в ОДНУ строку таблицы, поэтому «доров» — это сколько собранных сайтов живёт на поддоменах,
  а не сколько всего поддоменов было в выдаче;
- **кэш выдачи**: ответы источника на одинаковые запросы хранятся час (в консоли — 7 дней) и не тратят
  лимит: перезапуск через пять минут с другими фильтрами бесплатный, сбор через сутки — настоящий переобход; поэтому
  при повторе панель показывает «ответов из кэша» и предупреждает, что к источнику не обращались;
  галочка **«Свежая выдача»** в настройках отключает кэш на этот сбор (в консоли `--no-cache`);
- **уникальные домены**: результаты сводятся по регистрируемому домену — если в разных запросах
  встречаются разные поддомены одного домена, берётся один (галочка «дедуп по домену», по умолчанию вкл);
- **предпросмотр при сборе**: на этапе «Сборка» (галочка «делать скриншот главной») по каждому
  уникальному домену делается **скриншот главной** (или пишется ошибка) — сразу видно объём будущей
  выгрузки и где **наши** сайты (помечены «исключён как наш»), ещё до полной выгрузки; нужен Chromium.
  В таблице результатов у каждого сайта — **превью** (клик увеличивает в окне), **крестик ✕** чтобы
  убрать неподходящий сайт; над таблицей — **статистика** по оставшимся (сколько наших — с долей от
  таблицы, как во вкладке «Статистика», — сколько проблемных, сколько без ошибок; после выгрузки — ещё и разбивка по числу страниц: сколько одностраничников, сколько
  9- и 10-страничников — та же разбивка в сообщении задания и в журнале) и кнопки массовой чистки: **«Убрать наши»** (работает сразу после сбора, по превью — наши
  тогда даже не выгружаются), **«Перепробовать без превью»** (сайты, у которых
  на сборе не открылась ни одна страница: ещё несколько заходов на главную, каждый — **с другого прокси
  и под другим браузерным агентом**, с растущим таймаутом; уже открытые сайты и наши шаблоны не трогаются.
  Часть сайтов открывается со второго-третьего раза: подвис прокси, сработал лимит, антибот пустил
  «посетителя», но не робота. Столько же попыток делается и **автоматически в конце сбора** —
  `visit.preview_retries`, по умолчанию 2, 0 отключает), **«Убрать без превью»** (те же сайты, но
  выбросить их из списка — чтобы идти на выгрузку без них) и **«Убрать с 404 > N»**
  (сайты, у которых страниц с ошибкой 404 больше порога; по умолчанию 4). Любая кнопка массового
  «Убрать», которая заберёт **весь** видимый список, сначала спрашивает подтверждение, а таблица после
  этого не пропадает: остаётся строка «Все сайты убраны… нажмите «вернуть все»» и сама ссылка возврата.
  **Тип вёрстки** определяется
  сразу после сбора по HTML главной (превью), без скриншотов: у сайта в таблице стоит метка «7–9 стр.» или
  «12–15 стр.» — два семейства шаблонов сети (первое: шапка с брендом, телефон «+7 (495)…» и
  «Круглосуточно», панель фильтров «Все игры / Провайдеры», вступление перед заголовком, облако
  «Навигация»; второе: «Логотип бренд», меню с эмодзи, крошки «🏠 Главная», карточки «Куда перейти»,
  всплывающие «выигрыши», чат 24/7 и приветственный попап), остальные — «без категории» (рандомные).
  В статистике над таблицей — «по типу вёрстки: 7–9 стр. — N, 12–15 стр. — M, без категории — K», та же
  разбивка в журнале («Итого по типу вёрстки»). Галочки **«оставить: 7–9 стр. / 12–15 стр. / без
  категории»** и кнопка **«Оставить выбранные»** убирают из таблицы сайты снятых типов — можно оставить
  одну категорию, две или все (обратимо, «вернуть все»); наших сайтов это не касается — для них «Убрать
  наши». Число страниц в таблице сверяется с диском: если файл успешно скачанной
  страницы пропал, строка показывает «нет файла на диске: N», сайт считается проблемным и «Докачать»
  перекачивает именно эти страницы; при докачке папка сайта сливается из всех бакетов в одну, а после
  очистки в журнале видно, какие страницы остались «без статьи». Прошлый сбор не пропадает:
  после обновления страницы, перезапуска панели или обновления скрипта таблица берётся из `sites.json`,
  а сбор, который ничего нового не отобрал, прошлый список не затирает — с ним можно продолжать. Удаление **окончательное и сквозное**: убранный сайт исчезает из списка, его папки переезжают в
  `runs/current/removed/`, и он не всплывёт ни на докачке, ни на выгрузке, ни на очистке; «вернуть все»
  возвращает и строки, и папки. Новый сбор начинает список заново. Кнопка **«Очистить всё»** чистит
  контент по **оставшимся**;
- **два шага без выпадающего списка этапов** (вкладка «Главная»): кнопка **«Собрать сайты»**
  стоит рядом с запросами (шаг 1 — домены из выдачи + скриншоты главной), а кнопка **«Выгрузить
  страницы оставшихся»** — над таблицей результатов (шаг 2 — открывает в браузере и сохраняет
  страницы **ровно тех сайтов, что сейчас в таблице**: убранные крестиком или галочками типов не
  качаются, и ничего сверх таблицы тоже — панель передаёт заданию список хостов из таблицы; таблица
  вмещает до 5000 сайтов, если список длиннее, заголовок «Результаты» говорит «показаны первые N из M»);
- **очистка контента — кнопками в таблице результатов**: из скачанных страниц делает **шаблоны
  статей** строго по шагам мануала и в его порядке: **1** тело статьи = **контентный блок** страницы
  (`<main>`, иначе всё тело) без каркаса сайта — шапка, меню, крошки, подвал (облако «Ключевые темы»,
  «О портале», «Навигация»), попапы и виджеты (герой-баннер, джекпоты, «последние выплаты», таймеры,
  каталог слотов, CTA) удаляются целиком; начало — после `</h1>`, но если перед h1 стоит текст статьи
  (вводные абзацы, как на 7–10-страничниках), берётся всё с начала блока, а h1 становится h2; конец —
  «Популярные запросы» (всегда) или блок «О компании»/«Контакты» с реквизитами (телефон, e-mail,
  лицензия, ©) — раздел «О портале» посреди статьи без реквизитов остаётся; облако «Похожие запросы»
  посреди текста убирается как блок (текст после него остаётся); плюс **FAQ вторым потоком** — блок
  вопросов-ответов вне среза (после `<main>`, после «Популярных запросов») или только в JSON-LD
  вынимается и приклеивается, чтобы подстановка прошла и по нему, кнопки-вопросы становятся `h3`;
  убирается мусор (картинки/медиа, формы и кнопки, модалки, контакты, облако тегов, панель фильтров);
  всё остальное между шапкой и подвалом — контент и по умолчанию **остаётся**: герой-баннер, джекпоты,
  таймеры, CTA-блоки, «последние выплаты», карточки игр между разделами статьи, «похожие разделы».
  Галочка «При очистке убирать виджеты и каталоги слотов» в настройках (в консоли `--remove-widgets`,
  только каталоги — `--remove-slots`) включает их удаление; текст про слоты и FAQ остаются в любом случае; **2** подстановка переменных по **всему** — и по телу, и по FAQ: домен вместе с
  поддоменом → `%domain_name%`, дата → `%date%`, бренд → `%brand_name_ru%` / `%brand_name_en%`; чужой
  незаполненный плейсхолдер `{NAME}` («Где {NAME} выигрывает чаще») → случайное имя, в каждом месте своё;
  **3** снос служебного (`script`, `style`, `meta`, `link`, `noscript`, `img`, `hr`, `br`, `caption`);
  **4** развёртка контейнеров (`div`, `section`, `article`, `span`, `thead`/`tbody`… — тег снимается,
  «голый» текст, оставшийся без тега, заворачивается в `p`, плашки-бейджи разделяются пробелом,
  содержимое остаётся); **5** `em`/`i` → обычный текст, `b` → `strong`; **6** `h1` → `h2`, `h4`–`h6` →
  `h3`; **7** снятие всех атрибутов, кроме `href` у ссылок; **8** ссылки: внутренние → один из путей
  `/vhod`, `/registracia`, `/`, `/app`, `/slots`, `/zerkalo` (главная — `/`, не `/main`), внешние —
  в обычный текст. На выходе — чистый семантический HTML без классов, стилей и пустых промежутков.
  **Бренд определяется автоматически** (английский — из домена/`canonical`, русский — по тексту через
  транслитерацию, в том числе из двух слов — «Вулкан Вегас», «Мани Икс»), с учётом регистра, смешения
  латиницы/кириллицы (`STAKE`≡`STAKЕ`) и падежей своего бренда («Криптобосса», «в Вулкане Вегасе»);
  слитная метка бренда ловит и раздельное написание («cryptoboss» → «Crypto Boss»), не задевая обычные
  фразы; бренд ищется по всем страницам сайта, а не только по главной, поэтому находится, даже если
  главная оказалась заглушкой 18+ или редиректом. **Посторонние бренды** (другие казино в тексте) тоже
  заменяются — по встроенному списку известных брендов (дополняется файлом `brands.txt`). У каждого
  сайта в таблице есть кнопка **«Очистить»** — смотрите скриншот и жмёте,
  очищенные статьи ложатся в папку **`runs/current/content/<N>-стр/<сайт>/`** (N — число очищенных
  страниц), ничего не скачивается; а кнопка **«Очистить всё»** (над таблицей) чистит сразу все
  **оставшиеся** сайты по тем же папкам (наши и убранные крестиком исключены). «Очистить всё» идёт **фоном с прогрессом** («N из M сайтов»), как сбор и выгрузка — хоть 250 сайтов,
  без таймаутов, таблица не сбрасывается; контент убранных крестиком сайтов удаляется, а каждый сайт
  чистится заново поверх своей прошлой версии, поэтому лишнего в результате не остаётся. Части,
  очищенные в прошлых заходах того же сбора, сохраняются (чистый лист делает только новый сбор). Кнопка **«Скачать архив контента»** (рядом с «Очистить всё», появляется,
  как только на диске есть очищенные статьи, в подписи — сколько статей и сайтов) отдаёт всё содержимое
  `runs/current/content/` одним zip-архивом с теми же папками `N-стр/сайт/страница.html` — распакуйте его в
  нужную папку; архив собирается в момент нажатия (расширением zip в PHP, а без него — системным tar в
  Windows 10+/macOS). Массовая очистка в архив доступна и из консоли — `php bin/clean-content.php`;
- **докачка при ошибках**: если часть сайтов не выкачалась из-за ошибок (таймаут, нет соединения,
  блок/Cloudflare, SSL, DNS), над таблицей появляется кнопка **«Докачать с ошибками (N)»** — она
  заново выкачивает **только упавшие страницы** этих сайтов, **уже скачанные не трогает**, и пробует
  их **несколькими заходами через разные прокси** (с нарастающим таймаутом). Один из заходов пробует
  адрес **без языкового префикса** (`/ru/app → /app`) — иногда с префиксом отдаётся 404, а без него
  страница открывается. Ошибки «дубликат» повтором не чинятся; «страница не найдена (404)» чинится
  только когда у адреса есть языковой префикс (его-то и пробуем убрать). Число в кнопке — ровно те
  сайты, у которых есть что добрать; если добирать нечего, кнопка у сайта так и говорит («Нечего
  докачивать»), а после докачки в статусе видно результат: «добрано X из Y стр.» либо «нечего
  добирать» — чтобы не казалось, что докачка не запустилась;
- **сайты с фильтром по посетителю** (403 / «проверка браузера» даже с нашим агентом): по умолчанию мы
  ходим на сайты **роботом Яндекса** — так видно страницу такой, какой её отдают поисковику. Часть
  сайтов именно робота и не пускает: отдаёт 403 или заглушку антибота, и не получается даже снять
  скриншот. Теперь на **повторе меняется не только прокси, но и User-Agent**: приходим обычным
  браузером из списка, каждая следующая попытка — другой браузер. Если под браузером главная
  открылась, **остальные страницы этого сайта сразу идут под ним** (не тратим попытку на заведомый
  отказ), и докачка тоже начинает с рабочего агента. Где это сработало, видно в отчёте: в строке
  статистики — «под браузером (робота не пустили): N стр. на M сайтах», в раскрытии строки сайта у
  такой страницы стоит пометка **«под браузером»**, то же пишется в лог и в сообщение после выгрузки.
  Отключается в `config.php`: `'visit' => ['retry_user_agents' => false]` — тогда всегда ходим одним
  агентом;
- **подборка офферов вместо сайта** (сайт прячет себя): часть сайтов отдаёт не своё содержимое, а
  **витрину чужих бонусов** — «В подборке 6 офферов», кружки с брендами и кнопками «ЗАБРАТЬ БОНУС»,
  бегущая строка «7K КАЗИНО CASINO — 300 000 ₽ 500 FS» и внизу «18+ Азартные игры являются
  развлечением. Проверяйте условия бонуса партнёра перед регистрацией». Настоящий сайт за такой
  заглушкой показывается другим посетителям. Теперь такая страница **не сохраняется как контент**:
  она перезапрашивается **с другого IP (прокси) и под другим User-Agent** — и если настоящий сайт
  покажется, скачается именно он. Если сайт отдаёт витрину всем, он остаётся в таблице с меткой
  **«подборка офферов»** (скриншот сохраняется, чтобы было видно глазами), в строке статистики видно
  «подборок офферов вместо сайта: N», а кнопка **«Убрать подборки офферов (N)»** убирает их пачкой
  (обратимо, «вернуть все»). Витрина определяется по формулировкам («оффер», «условия бонуса
  партнёра»), по повторяющимся карточкам чужих брендов и по короткому тексту — у настоящего сайта на
  главной есть свой текст, поэтому длинные страницы витриной не считаются никогда. Отключается в
  `config.php`: `'visit' => ['detect_offer_walls' => false]`;
- **раскрытие строки сайта**: клик по колонке «Скачано» (появляется стрелка ▸) разворачивает под
  доменом **список всех его страниц** с результатом каждой — что скачалось (OK) и что упало и по какой
  причине (404, таймаут, блок, дубликат), со ссылками на сохранённые HTML/скрин. Там же кнопка
  **«Докачать этот сайт»** — перезапустить выгрузку **только** этого домена;
- **обход меню сайта** (галочка «Скачивать все страницы из шапки сайта»): на этапе выгрузки
  открывается не одна страница, а все страницы из меню — **и в шапке, и в подвале** (footer),
  начиная с главной, только в пределах **того же поддомена** (`www` считается тем же хостом);
  ссылки меню на **другие поддомены** (соседние бренды сетки) и на другие сайты пропускаются. Но
  если **главная сама редиректит** на бренд-поддомен своего же домена (сайт собран по
  `casinozsd.buzz`, а он ведёт на `kush.casinozsd.buzz`) — это **не** уход на чужой сайт: страница
  сохраняется, а меню разбирается уже на этом поддомене (на чужой домен редирект по-прежнему
  отбрасывается). Карты сайта (`htmlmap`, `sitemap`, `sitemap-all.xml`) и файлы-ресурсы (`.xml`,
  `.pdf`, картинки …) — тоже; «циклы» переключателя языка (`/RU-ru/RU-ru/…/app`) **схлопываются**,
  так что реальная страница за циклом (`app`) качается один раз; языковой префикс не плодит копий
  (`/promo` и `/RU-ru/promo` — одна страница, без `promo-2`); страница больше 2 МБ обрезается (гигантский
  DOM больше не роняет сбор по памяти); главная не сохраняется дважды
  (ссылка меню на «/» не создаёт `main-2`), и вообще **один файл на имя страницы**: `/vhod`, `/vhod.html`,
  `/vhod?ref=…`, `/Vhod` — это одна страница «vhod», второй вариант не качается и при докачке не добирается
  (никаких `vhod-2`, `registracia-2`); лимит — «Макс. страниц на сайт»;
  - **повтор при любой ошибке через другой прокси**: если страница не открылась (таймаут, сеть),
    вернула код блокировки (403/429/5xx) или это страница-заглушка антибота (**Cloudflare**,
    DDoS-Guard и т.п.) — загрузка повторяется через **другой прокси** (`visit.retries`, по
    умолчанию 2); страницы-блокировки **не** сохраняются как контент, а помечаются ошибкой
    «заблокировано»;
  - **файлы называются коротко по URL** — по последнему сегменту адреса: `/registracia` →
    `registracia.html`, `/catalog/plastikovye/` → `plastikovye.html`, главная → `main.html`;
  - **одна и та же страница не качается дважды**: адреса-алиасы (`/`, `/index.php`, `/about` и
    `/about/`) сводятся к одному и открываются один раз;
  - **одностраничники и дубликаты не качаются дважды**: сначала открывается главная, затем
    одна пробная страница из меню; если она сильно совпадает с главной (порог `visit.similarity`,
    по умолчанию 0.9) — сайт считается одностраничником и остальные страницы не открываются;
    совпадающие между собой внутренние страницы тоже отбрасываются;
  - **скриншот — только для главной** (по ней и смотрят сайт); внутренние страницы сохраняются
    как HTML без картинок;
  - **заглушки не путаются с дубликатами**: экран проверки возраста (18+), cookie-стена или
    «включите JavaScript» выглядит одинаково на всех страницах, но за ним контент разный.
    В Chromium (Playwright) такая заглушка по возможности проходится автоматически (нажимается
    «Да / Подтверждаю / Принять»), а если пройти не удалось — страницы всё равно **не** схлопываются
    в один и помечаются как «заглушка (проверка возраста/куки)»;
  - **папки по числу страниц**: готовые сайты раскладываются в `out/pages/<N>-стр/<сайт>/`
    (`1-стр`, `7-стр`, `11-стр` …) — сразу видно, сколько уникальных страниц у сайта;
- **исключение своих шаблонов**: сайты, которые вы сами размещаете, можно не собирать и не
  скачивать — они опознаются по устойчивым меткам (путь к ассетам, домен размещения, токен
  проверки из `<head>`), не завися от меняющихся кодов/стилей (QR, оформление). По умолчанию уже
  включена метка `/uploads/brands/` (общий путь к ассетам шаблона — ловит все бренды на любых
  доменах); дополнительные точечные метки (конкретные домены, токены) удобно держать в
  **панели: «Настройки» → «Метки наших шаблонов»** (по одной на строку — самый простой путь, ничего
  править на диске не надо; метки остаются только на вашем компьютере), либо в файле
  `own-markers.txt` (по одной на строку, файл не коммитится), либо в `filters.own_markers`. Метка ищется
  не только в HTML и в адресе сайта, но и **по всей цепочке редиректов**: если ваш дор сначала уводит на
  свой редиректор, а тот дальше — на чужую партнёрскую ссылку, то в конечном адресе редиректора уже нет,
  и опознать сайт можно только по промежуточному хопу. Достаточно вписать домен редиректора (или просто
  его имя) в метки: метка **без «/»** считается именем и ищется по
  границам слова, так что `faro` поймает `faro.com`, `go.faro.net` и `casino-faro.ru`, но не заденет
  чужой `safaro.ru`; метка **с «/»** — это путь (`/uploads/brands/`) и ищется как раньше, подстрокой.
  По адресам сайт проверяется **всегда — даже если страница не открылась** (таймаут, обрыв, антибот):
  цепочка редиректов известна и без страницы, а раньше вся проверка шла только по сохранённому HTML,
  и до нашего дора, до которого не достучались, она не доходила — такие сайты переставали считаться
  нашими. Такой
  сайт в отчёте помечается **«исключён как наш»**; HTML не сохраняется, но **скриншот главной
  остаётся** (в папке `out/pages/наши/<сайт>/`) — чтобы проверить глазами; метки-домены отсеиваются
  ещё на этапе сбора. Для **статистики** рядом есть второй файл — `own-domains.txt` (домены наших
  сайтов, по одному в строке): по нему наши узнаются даже среди повторов, которые мы уже не открываем;
- **докачка вытаскивает и полностью закрытые сайты**: если при выгрузке у сайта не открылось
  **ни одной** страницы, повтор не тратит первую попытку на робота (ему уже отказали) и сразу идёт
  браузером, пробует не только адрес из выдачи, но и **корень сайта** (адрес из выдачи бывает мёртвой
  глубокой ссылкой), а когда главная наконец открывается — **разбирает её меню и добирает внутренние
  страницы**. Раньше такой сайт навсегда оставался «1 стр.»: меню читается сразу после главной, а её
  тогда не было, и повтор чинил только её саму;
- **сайт увёл на чужой домен**: его страница как страница этого сайта не сохраняется (в отчёте
  «редирект на другой сайт: …» с конечным адресом), но **скриншот остаётся** — видно превью и видно,
  куда именно увёл редирект;
- **отчёт по каждому сайту**: сколько страниц скачано, либо **текст ошибки с причиной** (таймаут,
  код ответа, редирект…), либо «исключён как наш»; ссылки открыть сохранённый HTML и скриншот;
- **повторять сбор каждые N часов** — таймер: панель раз в N часов запускает сбор заново
  (и каждый раз добавляет в результат только новые домены);
- видеть прогресс (сбор → фильтрация → открытие сайтов), журнал и таблицу результатов,
  скачать `sites.csv`, `sites.json`, `domains.txt`.

Схема работы: **этап 1** — проходим XMLStock по всем запросам (топ N) → фильтруем домены
(дедуп по домену + пропуск уже собранных из базы) → сохраняем новые домены; **этап 2** —
выгрузка: открываем все собранные сайты в браузере. По таймеру этап 1 повторяется каждые N часов
и добавляет только новые домены.

Панель — надстройка над теми же командами (`bin/run-job.php` выполняет один сбор и пишет
прогресс в `runs/current/status.json`); всё, что делает панель, доступно и из консоли.

## Источники выдачи

| Источник | Как включить | Что нужно | Особенности |
|----------|--------------|-----------|-------------|
| Yandex Search API (по умолчанию) | `source => 'api'` | каталог Yandex Cloud, сервисный аккаунт с ролью `search-api.webSearch.user`, API-ключ (`YANDEX_FOLDER_ID`, `YANDEX_API_KEY`) | официальный платный API, до 100 сайтов на страницу, стабильный XML-формат |
| XMLStock | `source => 'xmlstock'` или `--source=xmlstock` | `XMLSTOCK_USER` и `XMLSTOCK_KEY` из личного кабинета xmlstock.com | тот же формат Яндекс.XML, платно за запрос, без настройки Yandex Cloud; режим `xmlstock.mode`: `xml` (до 100 сайтов на странице) или `live` — живая выдача Яндекса через XMLStock (по 10 сайтов на странице, свои прокси не нужны) |
| Живая выдача | `source => 'live'` или `--live` | свои прокси (`proxies.txt`) | страница yandex.ru как у пользователя, около 10 результатов на страницу, вёрстка Яндекса меняется |

### Yandex Search API

1. В консоли Yandex Cloud выберите каталог — его идентификатор и есть `YANDEX_FOLDER_ID`.
2. Создайте сервисный аккаунт с ролью `search-api.webSearch.user` и API-ключ для него — `YANDEX_API_KEY`.
   Вместо ключа можно использовать IAM-токен (`YANDEX_IAM_TOKEN`), он живёт 12 часов.
3. Квоты: 10 запросов в секунду, 10 000 синхронных запросов в час, не более 250 результатов на запрос.

Документация: <https://yandex.cloud/ru/docs/search-api/>.

### XMLStock

Сервис отдаёт выдачу Яндекса в формате Яндекс.XML. В `.env` укажите
`XMLSTOCK_USER` и `XMLSTOCK_KEY`; в разделе `xmlstock` конфигурации можно
задать домен поиска (`domain`, например `yandex.kz`), тип устройства
(`device`) и любые дополнительные параметры сервиса (`extra_params`).
Параметры поиска (`region`, `groups_on_page`, сортировка) общие с API.

У XMLStock два вида выдачи — `xmlstock.mode` (в панели — поле «Выдача»,
в консоли `--xmlstock-mode=xml|live`):

- `xml` (по умолчанию) — Яндекс.XML: `https://xmlstock.com/yandex/xml/`, до 100 сайтов
  на странице, дешевле;
- `live` — живая выдача Яндекса, как её видит обычный пользователь:
  `https://xmlstock.com/yandexlive/xml/`, тот же формат ответа, но всегда по 10 сайтов
  на странице (ограничение Яндекса) и без параметров группировки, поэтому «топ N»
  собирается с N/10 страниц (панель считает это сама). В отличие от источника
  «Живая выдача», свои прокси не нужны — страницы запрашивает XMLStock.
  Адрес переопределяется переменной `XMLSTOCK_LIVE_ENDPOINT`.

### Живая выдача

Скрипт запрашивает страницу `yandex.ru/search/?text=…&lr=…&p=…` с обычными
заголовками браузера, разбирает HTML и отдаёт результаты в тот же конвейер
фильтров. Как это устроено:

- Прокси берутся из общего списка `proxies` в конфигурации, файла `proxy_file`
  (`--proxies=FILE`) и опций `--proxy=…`; основной формат строки —
  `http://host:port:user:pass`, остальные описаны в `proxies.example.txt`.
  Без прокси — прямое подключение; строка `direct` добавляет прямое подключение
  в общую очередь. Тот же список по кругу используется для визитов на сайты.
- Прокси используются по кругу (`requests_per_proxy` запросов подряд через один);
  между запросами через один прокси выдерживается пауза `delay_ms` плюс случайная
  добавка `jitter_ms`, между любыми запросами — не меньше `min_gap_ms`.
- Каждому прокси назначаются постоянный User-Agent и своя банка cookies.
- **Капча не обходится.** Прокси, получивший капчу, ставится на паузу на
  `captcha_cooldown` секунд, запрос повторяется через следующий прокси
  (`attempts` попыток). Если все прокси на паузе дольше `max_wait`, прогон
  останавливается, результаты сохраняются. Сетевые ошибки дают паузу
  `error_cooldown`, после `max_proxy_failures` ошибок подряд прокси отключается.
- Ответы API Яндекса и живая выдача могут отличаться: живая страница
  персонализирована под регион и историю, поэтому для сравнения используйте
  один регион (`--region`) и несколько запусков.

Перед прогоном полезно проверить прокси: каждый делает один запрос к выдаче,
и в ответе видно, получена ли выдача, капча или ошибка:

```bash
php bin/yandex-sites.php --check-proxies --proxies=proxies.txt
```

Если Яндекс изменил вёрстку и результаты перестали разбираться, запустите с
`--save-html=debug` — все полученные страницы (включая капчу) сохранятся вместе
с метаданными (`*.json`: прокси, код ответа, конечный URL, тип страницы), и
проверьте разбор сохранённой страницы:

```bash
php bin/yandex-sites.php --live --proxies=proxies.txt -q "пластиковые окна" --limit=1 --no-cache --save-html=debug -v
php bin/yandex-sites.php --parse-html=debug/пластиковые_окна-p1-…-serp.html
```

Команда показывает тип страницы (выдача, капча, пусто), найденные результаты и
признак следующей страницы — по ней удобно поправить `src/Live/HtmlResponseParser.php`.

Юридическая оговорка: автоматические запросы к странице поиска ограничены
пользовательским соглашением Яндекса; официальные пути — Yandex Search API и
XMLStock. Живой режим предназначен для небольших объёмов через собственные прокси
и с умеренной скоростью.

## Быстрый старт

```bash
# запросы из файла, настройки из config.php, результаты в out/
php bin/yandex-sites.php queries.example.txt

# XMLStock, две страницы по 50 результатов, регион Санкт-Петербург
php bin/yandex-sites.php --source=xmlstock --pages=2 --region=2 queries.txt

# живая выдача через прокси, 3 страницы (около 30 результатов на запрос)
php bin/yandex-sites.php --live --proxies=proxies.txt --pages=3 queries.txt

# зайти на каждый отобранный сайт браузером, сохранить HTML и скриншот
php bin/yandex-sites.php queries.txt --visit

# по три визита на сайт с разными прокси и User-Agent — увидеть разные версии страницы
php bin/yandex-sites.php queries.txt --visit --variants=3

# только первые 3 запроса, подробный вывод, все результаты с причинами отклонения
php bin/yandex-sites.php queries.txt --limit=3 --raw -v

# подготовка контента из скачанных страниц (out/pages → out/content + архив)
php bin/clean-content.php --brand-ru=криптобосс --brand-en=cryptoboss --brands=STAKE --zip=out/content.zip
```

По завершении в консоль выводится сводка: сколько запросов обработано, сколько
результатов отклонено и по каким правилам, первые отобранные сайты, статистика
по прокси и визитам, пути к файлам. С `-v` результаты печатаются по мере получения.

## Файл запросов

Один запрос на строку, пустые строки и строки с `#` пропускаются, дубли
удаляются. Допустимы операторы Яндекса, например `окна пвх site:msk.ru`.
Максимальная длина запроса — 400 символов.

## Настройка (`config.php`)

Файл возвращает массив; все ключи необязательны, пример с комментариями —
`config.example.php`. Разделы:

| Раздел | Что настраивает |
|--------|-----------------|
| `source` | источник выдачи: `api`, `xmlstock`, `live` |
| `api` | Yandex Search API: версия (`rest`/`xml`), доступ, пауза между запросами, повторы |
| `xmlstock` | режим (`xml` / `live` — живая выдача через XMLStock), адреса, доступ, домен поиска, устройство, дополнительные параметры |
| `proxies`, `proxy_file` | общий список прокси для живой выдачи и визитов (по кругу) |
| `live` | домен, паузы, попытки, паузы после капчи и ошибок, cookies, User-Agent |
| `search` | регион, число страниц, сайтов на странице (API/XMLStock), группировка, сортировка, свежесть |
| `cache` | каталог и время жизни кэша ответов |
| `filters` | правила отбора результатов; `own_markers` / `own_markers_file` — метки своих шаблонов («исключён как наш») |
| `site_check` | HTTP-проверка отобранных сайтов |
| `visit` | визиты на сайты: драйвер, число вариантов, прокси, Referer, скриншоты, каталог, обход шапки (`crawl`, `max_pages`, `similarity`) |
| `output` | каталог и имена файлов, разделитель CSV, BOM для Excel |

Параметры `--pages`, `--region`, `--groups`, `--delay`, `--out`, `--source`,
`--proxies`, `--visit-driver`, `--variants` в командной строке переопределяют
значения из файла.

## Правила отбора

Правила из раздела `filters` применяются к каждому результату выдачи;
результат отклоняется первым сработавшим правилом, причина попадает в сводку
и в `results.csv` (при `--raw`).

| Правило | Описание |
|---------|----------|
| `max_position` | учитывать только первые N результатов каждого запроса |
| `allowed_tlds` | разрешённые зоны, например `['ru', 'рф', 'su']`; пусто — любые |
| `include_domains` | если задано — берутся только эти домены (например, свои сайты для проверки позиций) |
| `exclude_domains` | исключения; по умолчанию — список агрегаторов, маркетплейсов, соцсетей, СМИ (`DefaultExclusions::LIST`) |
| `url_must_match`, `url_must_not_match` | регулярные выражения по URL страницы |
| `title_any`, `title_all`, `title_none` | хотя бы одно / все / ни одно из слов в заголовке |
| `snippet_any`, `snippet_none` | то же по заголовку, описанию и пассажам вместе |
| `unique_by` | считать сайтом хост (`host`, поддомены отдельно) или домен (`domain`; поддомены одного домена второй раз не берутся) |
| `domain_scope` | какие домены брать: `all` — любые, `root` — только корневые (`example.ru`), `subdomain` — только поддомены (`shop.example.ru`) |
| `min_queries` | сайт должен встретиться минимум в N разных запросах — отсекает случайные сайты |
| `min_hits` | минимальное число попаданий в выдачу |

Шаблоны доменов: `example.ru` — домен и поддомены, `*.example.ru` — только
поддомены, `=example.ru` — точное совпадение, `/^shop\d+\./i` — регулярное
выражение. Шаблоны текста — подстрока без учёта регистра или регулярное
выражение в разделителях (`'~окн[аы]~iu'`, для кириллицы нужен флаг `u`).
Шаблоны URL — только регулярные выражения.

Пример: найти сайты производителей, отбросив агрегаторы и форумы, и оставить
только те, что попали в выдачу минимум по двум запросам:

```php
'filters' => [
    'allowed_tlds' => ['ru', 'рф'],
    'exclude_domains' => [...DefaultExclusions::LIST, 'competitor.ru'],
    'url_must_not_match' => ['~/(forum|blog|news)/~i'],
    'title_none' => ['форум', 'отзывы', 'вакансии'],
    'min_queries' => 2,
],
```

## Проверка сайтов

Включается флагом `--check-sites` или `site_check.enabled = true`. Отобранные
сайты запрашиваются параллельно (`concurrency`), проверяются:

- код ответа (`require_status`, по умолчанию только 200; https, затем http);
  запрос идёт с User-Agent робота Яндекса (`site_check.user_agent`);
- редирект на другой домен (`reject_offsite_redirect`);
- наличие всех шаблонов на странице (`page_must_match`), например телефона
  `'~\+7[\s\-(]*\d{3}~u'` или ссылки `mailto:`;
- отсутствие шаблонов (`page_must_not_match`): «домен продаётся», «сайт заблокирован».

Страницы в windows-1251 и других кодировках перекодируются в UTF-8 перед
проверкой. Результат проверки попадает в колонки `check_*` CSV и в JSON.
Проверка отсеивает сайты; визиты (ниже) ничего не отсеивают, а сохраняют страницы.

## Визиты на сайты

Включается флагом `--visit` или `visit.enabled = true`. Для каждого отобранного
сайта открывается страница из выдачи (`target => 'found'`) или главная
(`'root'`) с Referer страницы выдачи Яндекса по тому запросу, где сайт был
найден (`referer => 'serp'`; варианты `'yandex'`, `'none'` или свой URL).

Драйверы:

- **playwright** — headless Chromium через `tools/render-page.js`: выполняется
  JavaScript, ждётся загрузка (`wait_ms`), сохраняются HTML после рендера и
  скриншот (`screenshot`, `full_page`). Нужны Node.js и Playwright:

  ```bash
  npm install playwright
  npx playwright install chromium
  node tools/render-page.js --check    # проверка окружения
  ```

  Если Chromium установлен в нестандартное место, укажите `visit.browser_path`.
- **curl** — обычный HTTP-запрос без JavaScript; используется, когда Playwright
  недоступен (`driver => 'auto'`), или принудительно (`--visit-driver=curl`).

User-Agent по умолчанию — робот Яндекса:
`Mozilla/5.0 (compatible; YandexBot/3.0; +http://yandex.com/bots)`. Так первый
визит показывает страницу такой, какой сайт отдаёт её поисковику. Тот же
User-Agent используется для HTTP-проверки сайтов. Переопределить его для визитов
и проверки можно флагом `--user-agent="…"` или в `visit.user_agents` /
`site_check.user_agent`. Для запросов к самой выдаче Яндекса всегда используются
браузерные User-Agent (`live.user_agents`): своему роботу Яндекс выдачу не отдаёт.
Часть сайтов проверяет робота по обратному DNS адреса, а не по строке
User-Agent, поэтому «версия для робота» может совпасть с обычной.

Прокси для визитов берутся по кругу из общего списка `proxies` / `proxy_file`
(`visit.proxy => 'list'`, по умолчанию; `null` — всегда напрямую, строка —
один конкретный прокси): каждый следующий визит идёт через следующий прокси.

Разные версии страницы. Параметр `variants` (`--variants=N`) открывает каждый
сайт N раз: первый визит — как робот Яндекса, следующие — как браузеры из
списка `visit.user_agents` (по одному на вариант), каждый через свой прокси. Для каждого визита считается
отпечаток видимого текста страницы; в CSV колонка `page_variants` показывает
«разных версий/визитов» (например, `2/3`), в JSON у сайта есть список `visits`
с адресом, прокси, User-Agent, кодом ответа, конечным URL, заголовком, путями
к файлам и отпечатком, а также число `variants`. Если у сайта `2/2` при
`--variants=2`, он показал роботу и посетителю разные страницы (клоакинг или
персонализация).

Файлы: `visit.dir/<хост>/variant-1.html`, `variant-1.png`, `variant-2.html`, …
Ограничить число посещаемых сайтов — `max_sites`, одновременность и паузы —
`concurrency`, `delay_ms`.

## Кэш и повторные запуски

Ответы сохраняются в `cache/<источник>/` (по умолчанию на 7 дней). Повторный
запуск с теми же запросами и параметрами не обращается к источнику, поэтому
фильтры можно подбирать без затрат. `--offline` запрещает обращения к источнику
(запросы вне кэша пропускаются с предупреждением), `--no-cache` отключает кэш,
`--dry-run` показывает список запросов и сколько обращений потребуется.

## Результаты

`sites.csv` / `sites.json` — по одной строке на сайт, отсортированы по числу
запросов, в которых сайт встретился, затем по лучшей позиции:

| Колонка | Содержимое |
|---------|------------|
| `host`, `host_unicode`, `domain` | хост, он же в Unicode для кириллических доменов, регистрируемый домен |
| `url`, `title` | страница и заголовок с лучшей позицией |
| `best_position`, `best_query` | лучшая позиция и запрос, в котором она достигнута |
| `queries_count`, `hits`, `queries` | число запросов, число попаданий, список «запрос (позиция)» |
| `check_status`, `check_final_url`, `check_title`, `check_result` | итог HTTP-проверки, если она включена |
| `page_file`, `page_final_url`, `page_title`, `page_variants` | сохранённая страница первого визита и число разных версий |

`domains.txt` — просто список хостов для передачи в другие инструменты.
`results.csv` (флаг `--raw`) — все результаты выдачи с причиной отклонения.
В `sites.json` также сохраняются статистика прогона, ошибки, статистика прокси
и использованные настройки.

## Параметры командной строки

```
php bin/yandex-sites.php [опции] [queries.txt ...]

--queries=FILE        файл с запросами (можно несколько раз); файлы можно передавать и без опции
-q, --query="…"       запрос из командной строки (можно несколько раз)
--limit=N             обработать только первые N запросов
--source=api|xmlstock|live   источник выдачи;  --live — то же, что --source=live
--xmlstock-mode=xml|live     выдача XMLStock: Яндекс.XML (по умолчанию) или живая выдача (по 10 сайтов на странице)
--proxies=FILE        файл со списком прокси (общий для живой выдачи и визитов)
--proxy=АДРЕС         добавить прокси, например http://host:port:user:pass (можно несколько раз)
--check-proxies       проверить каждый прокси одним запросом к живой выдаче и выйти
--save-html=DIR       сохранять все страницы живой выдачи (и капчу) с метаданными для отладки
-c, --config=FILE     файл конфигурации (по умолчанию ./config.php, если есть)
-o, --out=DIR         каталог результатов (по умолчанию out/)
--pages=N             страниц выдачи на запрос
--groups=N            сайтов на странице для API/XMLStock, 1–100
--region=ID           регион поиска (213 — Москва, 2 — Санкт-Петербург, 225 — Россия)
--delay=MS            пауза между обращениями к источнику
--check-sites         HTTP-проверка отобранных сайтов
--visit               визиты на отобранные сайты с сохранением HTML и скриншотов
--visit-driver=X      playwright | curl | auto
--variants=N          визитов на сайт: первый — как робот Яндекса, следующие — как браузеры (и разные прокси)
--user-agent="…"      свой User-Agent для визитов и проверки сайтов вместо YandexBot
--raw                 записать все результаты с причинами отклонения
--no-cache            не использовать кэш
--offline             работать только по кэшу
--parse-html=FILE     разобрать сохранённую страницу живой выдачи (отладка)
--dry-run             показать запросы и настройки, ничего не запрашивать
-v, --verbose         подробный вывод;  --quiet — только ошибки
-h, --help            справка;  --version — версия
```

Коды выхода: 0 — успех, 1 — прогон прерван фатальной ошибкой источника
(результаты по обработанным запросам всё равно сохраняются), 2 — ошибка в
аргументах или конфигурации.

## Пробный запуск без ключей и прокси

В комплекте есть фейковый сервер, который изображает все три источника и
несколько «сайтов»:

```bash
FAKE_MODE=local php -S 127.0.0.1:8089 tests/fake-api-server.php &

# Yandex Search API
YANDEX_FOLDER_ID=demo YANDEX_API_KEY=demo \
YANDEX_REST_ENDPOINT=http://127.0.0.1:8089/v2/web/search \
php bin/yandex-sites.php -q "пластиковые окна" --no-cache -v

# живая выдача (домен поиска указывает на фейковый сервер) и визиты браузером
YANDEX_LIVE_DOMAIN=http://127.0.0.1:8089 \
php bin/yandex-sites.php --live -q "пластиковые окна" --pages=2 --delay=0 --no-cache -v

# XMLStock
XMLSTOCK_USER=demo XMLSTOCK_KEY=demo XMLSTOCK_ENDPOINT=http://127.0.0.1:8089/yandex/xml/ \
php bin/yandex-sites.php --source=xmlstock -q "пластиковые окна" --no-cache

# XMLStock, живая выдача (по 10 сайтов на странице)
XMLSTOCK_USER=demo XMLSTOCK_KEY=demo XMLSTOCK_LIVE_ENDPOINT=http://127.0.0.1:8089/yandexlive/xml/ \
php bin/yandex-sites.php --source=xmlstock --xmlstock-mode=live --pages=2 -q "пластиковые окна" --no-cache
```

Переменные `YANDEX_REST_ENDPOINT`, `YANDEX_XML_ENDPOINT`, `XMLSTOCK_ENDPOINT`,
`XMLSTOCK_LIVE_ENDPOINT` и `YANDEX_LIVE_DOMAIN` переопределяют адреса источников (пригодятся и для
прокси-шлюзов). Визиты в демо-режиме на «сайты» фейкового сервера не попадут:
адреса вида `http://okna-moskva.ru:8089/` нужно направить на 127.0.0.1 через
`visit.resolve` (см. `tests/IntegrationTest.php`).

## Обработка ошибок и лимитов

- Временные ошибки API (HTTP 429, 5xx, сетевые, код 55 «превышена частота»)
  повторяются с нарастающей задержкой (`api.retries`, `api.retry_delay_ms`).
- Фатальные ошибки (неверный ключ, HTTP 401/403, исчерпан лимит — код 32,
  закончились прокси в живой выдаче) останавливают прогон; уже собранные
  результаты сохраняются.
- Ошибка по отдельному запросу пропускает только этот запрос; после
  `search.max_consecutive_errors` ошибок подряд прогон останавливается.

```

Структура:

```

Чтобы подключить другой источник выдачи, реализуйте `RawFetcherInterface`
(сырой ответ по запросу и странице) и, если формат не Яндекс.XML,
`ResponseParserInterface`, затем передайте их в `Runner`.
